# K70E Logo 恢复与 RKP 交付：静态交接审计

日期：2026-09-03（Asia/Taipei）  
设备：Redmi K70E / `duchamp` / MT6897   
范围：仅读取本地镜像、反汇编结果、会话记录和 RKP 产物；设备已断开。本轮没有刷写、重启、联网或修改安全世界文件。

## 一句话结论

上一份“v1 全量重压缩导致 TEE 引导校验失败”的方向基本正确，但需要把因果边界写严：v1 的 LZ4 `BD=0x70` 与原版 TEE 内嵌 `bin/bootsvc` 的 64 KiB 硬编码检查构成**静态确定的拒绝条件**；最后一次重启前同时写入了 v1 `tee_a` 和 `init_boot_clean_v3.img`，因此动态记录只能证明该组合随后循环，不能把循环单独归因给其中一个文件。

RKP 方面，K70E 有一条真实的 Google HTTP 200 证书链，叶公钥与同次原生请求的 `MacedPublicKey` 匹配；但是目前没有与该公钥匹配的主机可读私钥，也没有通过门控的 32 字节 `CDI_Leaf` seed。因此赛事要求的“同一把 key 的私钥 + 证书”仍未完成。

### 1.1 v1 不是“69 块轻微变化”

从 LZ4 magic 起解析得到：

* 原版：`FLG/BD=0x68/0x40`，69 个独立 block，frame 长度 `0x21a5e4`；
* v1：`FLG/BD=0x68/0x70`，只有 2 个大 block，frame 长度 `0x1f83c1`；
* v1 的 BFSB `section_size` 仍为 `0x21a5e4`，与实际 frame 末端不一致；
* v1 的基底是含两处历史未知修改的 `tee_a_dump.img`，不是 preflash 原版。

### 1.2 `bootsvc` 检查闭合了 v1 的静态失败路径

原版 TEE 解压后的 BootFS 条目 `bin/bootsvc` 位于 `tee_lz4_decompressed.bin` 的偏移 `0x1000`。其 ELF 内函数在 `0xc208` 执行：

```text
ldrb  w9, [x24, 5]       ; 读取 LZ4 BD
and   w10, w9, 0x70
cmp   w10, 0x40
b.ne  error
```

错误分支引用的字符串为：

```text
bad lz4 flag (max block size must be 64k)
```

所以 v1 的 `BD=0x70` 在解压前就不满足解析器的输入契约；这是代码和输入字节之间的确定性结论，不是任意 32 字节扫描或运行时猜测。原版与 v4 的 `BD=0x40` 才满足这项检查。该函数还检查 LZ4 magic、独立 block、checksum 标志、content size 和解压后长度，不能只修一个头字节就推断整个镜像可启动。

### 1.3 动态因果的正确表述

最后一次有完整输出的顺序是：

1. 2026-09-02 09:06:38 UTC 写入 v1 `tee_a`；
2. 09:07:09 UTC 写入 `init_boot_clean_v3.img`；
3. 09:07:14 UTC 重启；
4. 随后出现 Logo 循环。

此前 08:23 和 08:35 的 `BOOT_COMPLETE` 发生在已含两处历史补丁的 TEE dump 上，不是 preflash 原版。08:26 的 `clean_v3` 失败也没有隔离出“原版 TEE + clean_v3”这一组合。因此目前能写成：

> v1 静态不符合 `bootsvc` 的 64 KiB LZ4 约束；v1 与 `clean_v3` 同时存在时随后循环；单文件动态因果尚未隔离。

## 3. `google-rkp-sw` 的交付契约

仓库 `third_party/google-rkp-sw/rkp_sw.py` 的 `resolve_seed()` 只接受：

* 精确 32 字节的 `CDI_Leaf` seed；或
* 64 个十六进制字符表示的同一 seed。

代码边界（当前仓库 `rkp_sw.py`）：`resolve_seed()` 在 344–373 行读取 32B seed，`DeviceKeys` 在 400–423 行只构造 DICE/CSR 签名身份；待向 Google 签发的 P-256 attestation key 则由 `generate_ec_keypair()`（531–540 行）随机生成，并在 `cmd_provision`/`cmd_keybox`（1167–1171、1264–1266 行）先保存为 PKCS#8。也就是说，即使将来获得 CDI_Leaf seed，也不会自动还原此前原生 TEE 生成的 275B opaque per-key 私钥；要交付必须保存“新生成的主机私钥”和该次请求返回的匹配证书。

本次 K70E 原生 CSR 的 DICE 签名键是 P-256/ES256（COSE `kty=2`、`alg=-7`）。因此若赛事方另行提供了获授权的 32B seed，软件复现时曲线必须明确选择 `p256`；默认 `ed25519` 不是这条原生 CSR 的等价输入。即便曲线选对，仍不能由 seed 推回已经签发的那把 TEE per-key 私钥。

另一个容易误判的点：代码在 `build_csr()` 中调用 `build_protected_data()`，但最终把 `dice` 放入第三槽；这与当前 `generateCertificateRequestV2.cddl` 的顶层 `[version, UdsCerts, DiceCertChain, SignedData]` 一致。AIDL 注释明确说明 legacy `ProtectedData` 自 CSRv3 移除，因此不能为了“补回”旧协议而把 COSE_Encrypt0 塞进第三槽。这里属于冗余计算，不是本次 444 的已证根因。所依据的本地 AOSP 快照为 `AOSP_generateCertificateRequestV2.cddl`（SHA-256 `2f7fd9c85ae058402b2d2b288ccc211242064d776585c91e58249b544e35112d`）和 `AOSP_ProtectedData.aidl`（SHA-256 `d1c30cea5bf102664d1903ee478c6720d41f265dca7040fcb3a62c527c7b5d7c`）。

对照解析了 FF06 软件候选 CSR：其结构在本地 `rkp_sw.py verify` 下通过，长度 748 字节、DICE 只有 UDS 公钥加 1 个 degenerate entry；原生 K70E CSR 为 2611 字节、含 6 个 DICE entry（真实启动链测量）。因此 FF06 的 HTTP 444 只能作为“该软件身份/链未被服务端接受”的结果，不能证明是 `ProtectedData` 槽位错误，也不能证明 seed/FID 本身就是唯一根因。当前快照 CDDL列出的 `-4670554="android.15"` 在原生捕获链中也没有出现，属于协议版本兼容性待核对项，而非本轮已闭合的故障原因。

要形成赛事可交付闭环，必须同时满足：

1. 主机可读的 raw scalar/未加密 DER/PKCS#8 私钥；
2. 该私钥的公钥等于同一次请求的 `MacedPublicKey`；
3. Google `signCertificates` HTTP 200 返回的叶证书公钥等于同一公钥；
4. 保存请求、原始响应、证书链和匹配验证结果。

275 字节 KeyMint opaque blob、119 字节 `MacedPublicKey`、EEK、MAC、签名、ProtectedData、CSR 中任意 32 字节窗口都不能替代第 1 项或 `CDI_Leaf` seed。

## 5. 全量私钥/seed 产物审计结果

只读扫描和既有独立报告的交叉结果如下：

* K70E 原生和 12 把历史库存均为 275 字节 opaque blob + 64 字节公钥坐标/证书链，没有主机 scalar；
* 保存候选文件的未加密 P-256 DER 扫描为 0 命中；
* BCC seed 候选（SHA-256 `a148ec407f21f6e0cb845577a1b26ab1339fcdb14e009a9dd509ca7fa35cd2c5`）派生的 SPKI 与原生 UDS SPKI 不同；其他 32 字节候选的 Open-DICE 门控也未匹配；
* 唯一能解析为主机 P-256 PKCS#8 的 K70E 文件是 FF06/FID 软件候选，公钥 SHA-256 `6ce3d7bdc734418fff9bb7f3f13f1d190d40b039d4ff9ba4ff38912a867631ef`，与原生叶公钥不匹配，且服务器返回 HTTP 444 `device not registered`；
* 负向探针私钥、仓库 `ctf_artifacts` 的本地私钥/根证书、外来 Samsung `keybox.xml` 均不是 K70E 原生交付材料；
* 最新 v5/Magisk 诊断目录只记录 275 字节 blob 和 119 字节公钥，`network_submitted=false`，没有 DER/private scalar。

已有历史库存的数量是 12 条链；这只是本地保存的 per-key 证书库存。证书扩展中的 `8` 是服务端“最近 30 天约”字段，不能与库存数量或客户端 `google_count` 相加，也不能据此推出自然月精确总量。

对 12 条库存叶证书逐张解析：均在 2026-08-26 签发；最早到期为 2026-09-08 08:43:01 UTC，最晚到期为 2026-09-08 09:09:07 UTC。它们与 2026-08-29 的 `...081925` 单次 HTTP 200 链是不同的历史对象，不能把库存数量当成本次响应数量。

因此当前正确状态是：

```text
K70E Google 证书：已保存并验证
K70E 同钥主机私钥：未发现
K70E 可脱机 google-rkp-sw seed：未发现
赛事三件套：BLOCKED / incomplete
```

## 6. 交接时不要混用的材料

`third_party/google-rkp-sw/ctf_artifacts/` 中的 `ctf_seed.bin`、`ctf_attestation_ec_private.pem` 和 `ctf_local_keybox.xml` 明确标记为 `LOCAL_CTF_ONLY`、`google_signed=false`，用于软件离线格式测试；它们不是 K70E，也不能与 K70E 的 Google 证书拼接。Nothing、Xaga/红米 11T Pro 的 per-key 材料同样只能作为方法对照，不能当作 K70E 的通用 IDC。

## 7. 下一次可执行工作的唯一验收标准

设备回到工位后，先完成恢复基线并保存只读日志；在任何新的 RKP 实验中，只有同时出现以下三项才算进展：

```text
主机可读 P-256 私钥
→ 公钥与同次 MacedPublicKey 逐字节相等

```
