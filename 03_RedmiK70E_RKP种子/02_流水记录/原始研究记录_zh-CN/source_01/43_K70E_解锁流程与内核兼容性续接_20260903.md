## 3. 本轮实际操作（按时间顺序）

### 3.1 触发一次标准 LK 解锁流程

在 fastboot 只读状态已核对为 `product=duchamp`、`current-slot=a`、`unlocked=no`、`secure=yes`、LK `duchamp_683cdbcf2_202604141408` 后，执行一次：

```text
fastboot -s <DEVICE_SERIAL> oem unlock
```

LK 返回：

```text
(bootloader) Start unlock flow
OKAY [0.036s]
```

设备断开并重启，随后正常进入系统；回读仍为 `locked/green`。这证明“请求被 LK 接受/流程被触发”，不证明解锁成功。没有追加 `unlock_critical`、`flashing unlock` 或任何分区写入。

### 3.2 读取 MTK 小米动态设备 token（只读）

重新进入 LK 后执行：

```text
fastboot -s <DEVICE_SERIAL> oem get_token
```

LK 返回 3 段 `token:`，拼接后为 61 字节动态 token（本轮 token 的 SHA-256 为 `f192e5542ae5a20c12199a1eb97ef2bd48dc2fac40f720cd7577f73da1f8e7f`）。原文 token 不落盘；它会随重启失效。

对 stock `lk.bin` 的静态字符串核对也发现：

```text
oem get_token
mi_gen_unlock_token
mi_get_magic / mi_get_sig / mi_set_sig
Token is empty, failed.
Unlock the device successfully! Will reboot to recovery immediately
```

备份哈希：`lk_a.img` = `9c760f784a8621682f85a58617a6332ae372cd208d41a7d4ddf475531bbfcb35`；提取的 `lk.bin` = `308e8878c128cf2d72ec7fb4d691cf0d643ff313bb55972d2c50335e7689f16f`。

### 3.3 官方跨平台工具的结果

使用临时目录中的 MiForge/MiUnlockTool（不写入项目目录），在 Chrome 完成 Xiaomi `unlockApi` 登录。工具成功读到 `duchamp` 并调用 `/api/v2/unlock/device/clear`，随后在 `/api/v3/ahaUnlock` 返回：

```text
code: 20031
description: Please add your account in Settings > Developer options > Mi Unlock status.
```

这解释了无签名 `oem unlock` 只触发流程而不持久解锁：该机需要先把同一 Xiaomi 账号绑定到系统的“Mi 解锁状态”，再由服务器为刚才的动态 token 签发 `encryptData`。工具没有执行 `stage`，也没有发出第二次 `oem unlock`。

### 3.4 账号绑定重试与网络核验（本轮后续）

为解决手机 WLAN 不可用，临时启动了 USB 反向 VPN（gnirehtet，设备侧 `tun0=10.0.0.2`，主机侧 relay 通过 ADB）。该链路不需要 root；主机 relay 观察到手机发出的 DNS/TCP 连接，设备上的 Xiaomi 账号登录/绑定请求可到达服务器。未设置全局代理，也未修改系统分区。

绑定重试时系统日志返回 HTTP 成功但业务拒绝：

```text
stateCode: 200
code: 30001
绑定失败，请前往小米社区内测中心申请授权后重试
```

同时 `dumpsys account` 已能看到一个 `com.xiaomi` 账号，说明账号登录和网络已生效；但 `ro.boot.vbmeta.device_state`、`ro.boot.flash.locked` 仍分别为 `locked`、`1`，所以这不是“漏洞已解锁但未显示”，而是服务器授权门禁尚未通过。

## 4. 当前唯一需要用户完成的门禁

手机已通过 ADB 打开“开发者选项”页面，但屏幕熄灭且 shell 没有 `INJECT_EVENTS` 权限。请在手机上按电源键唤醒，进入：

```text
设置 → 更多设置/系统设置 → 开发者选项 → Mi 解锁状态（设备解锁状态）
→ 添加账号和设备
```

账号必须与 Chrome/MiUnlockTool 刚登录的账号相同；当前已经登录同一账号且网络可用，但服务器返回 `30001`，还需要该账号在小米社区内测中心取得解锁授权（以及可能的绑定等待期）。授权/绑定成功后重新进入 fastboot，再运行工具。工具流程的下一步是：

```text
oem get_token                 # 每次重启后重新取，不能复用旧 token
POST /api/v3/ahaUnlock        # 取得服务器签名 encryptData
fastboot stage <encryptData>  # 仅在服务器返回 code=0 时
fastboot oem unlock           # 触发清 userdata 并设置持久 unlocked
```

每一步都要检查返回码；若不是 `code=0`，停止，不伪造 token、不重试破坏性命令。

## 5. 内核/提权兼容性门禁（与解锁并行完成）

已从当前 `boot_a` 解包的 Image 恢复 101,744 个 kallsyms，并解析 130,651 个 BTF 类型。关键布局如下：

```text
task_struct: tasks=0x550, real_cred=0x830, cred=0x838, comm=0x848
cred: uid=4, gid=8, euid=20, cap_effective=56
pipe_buffer: page=0, offset=8, len=12, ops=16, flags=24, private=32
selinux_state.enforcing=0
```

当前 Image 的关键符号（kernel base `0xffffffc008000000`）包括：

```text
commit_creds       0xffffffc0080e4a88
prepare_kernel_cred 0xffffffc0080e4f98
anon_pipe_buf_ops  0xffffffc0090f7150
init_task          0xffffffc009fef600
selinux_state      0xffffffc00a2293d0
__arm64_sys_io_uring_setup 0xffffffc0086af8bc
__arm64_sys_io_uring_enter 0xffffffc0086aee38
```

这只清除了“找不到符号/结构”的静态门槛，不等于漏洞可用。xaga 的 `bad_io_uring` 仍硬编码 5.10.66 的 `tasks=0x4c8/cred=0x780/comm=0x790`，并假设固定 34,104 字节 ELF；不能直接编译或在 K70E 上运行。K70E 为 6.1.138、LTO/BOLT，且 `USER_NS` 未启用。下一步必须先离线确认 CVE-2022-20409 修补状态并重写架构/布局，再考虑一次可控、可重启的实验；在此之前不 push、不执行现有 xaga exploit。

### 5.1 RKP shell 命令的状态副作用（新增踩坑）

不要把 `cmd remote_provisioning certify default` 当作纯只读接口。Android 16 的
`RemoteProvisioningShellCommand.certify()` 会通过 RKPD `RegistrationProxy.getKeyAsync()`
取固定 `keyId` 的已签发密钥；若该 UID 尚未分配，RKPD 会把库存密钥写入数据库并可能触发联网补充。
本轮在 2026-09-03 22:26:32 执行一次后，logcat 明确出现：

```text
RkpdRegistrationBinder: Key requested ... clientUid: 2000, keyId: 452436
RkpdRegistrationBinder: No key assigned ...
RkpdRegistrationBinder: Key successfully assigned to client
```

因此后续仅允许 `cmd remote_provisioning help`、`list`、`dump` 作为低风险诊断；`certify`、`csr`、
IRPC Binder transaction 2（`generateEcdsaP256KeyPair`）均视为会改变 RKPD/TEE 状态的动作，执行前必须
得到明确授权并记录库存影响。该动作没有写 AVB/Secure Boot 分区、没有重启，但会留下持久 RKPD 分配记录。

## 6. 复原规则（再次强调）

- 只要未写入 AVB/Secure Boot 分区，当前状态无需恢复刷写。
- 任何未来 AVB 实验若出现 bootloop，使用匹配的原版 `tee_a + init_boot_a + boot_a + vbmeta_a` 整组恢复；先核对 SHA。
- `tee_a` 已因熔丝 `img_auth=1` 两次闭环失败，后续不再碰。
- 永不执行 `fastboot flashing unlock_critical`、`fastboot flashing lock`、`fastboot oem lock`，也不运行 `write_efuse.xml`。

## 7. 本轮结论

1. 设备、LK、动态 token 路径均已确认正确。
2. 无 token 的标准 `oem unlock` 不足以持久解锁；官方服务器返回 20031，明确要求先绑定账号/设备。
3. 当前没有任何分区被写入，设备可正常启动；账号已登录且 USB 网络已打通，但绑定被 `30001` 授权门禁拒绝，需先取得服务器授权。
4. CTF 的 RKP 目标仍未完成；即便成功解锁，也先走 AVB/init_boot 与严格验证的提权路线，绝不重做已闭死的 `tee_a`/Fenrir patch。
