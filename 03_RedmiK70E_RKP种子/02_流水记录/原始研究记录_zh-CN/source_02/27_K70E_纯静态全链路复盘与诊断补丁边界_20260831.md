## 2. K70E 活动 RKP 密钥生成链（已由反汇编闭合）

原厂活动命令的静态边为：

```text
0xc94d8
  -> BL 0x61960  GenerateRkpKey
       -> 0x610e8  GenerateKey/工厂分发
            -> factory vtable +0x10
                 -> 0xa2fd0  EcKeyFactory::GenerateKey
                      -> 0xfb0f0    EVP_PKEY_new
                      -> 0x114fe0   P-256 group 选择
                      -> 0x116770   EC_KEY_set_group
                      -> 0x116c28   EC_KEY_generate_key
                      -> 0x116a28   EC_KEY_check_key
                      -> 0xfb3e0    EVP_PKEY_set1_EC_KEY
                      -> 0xa79d0    EvpKeyToKeyMaterial
                      -> 后续 CreateKeyBlob / opaque handle
       -> 0xa7b88  GetEcdsa256KeyFromCert（只取公钥 X/Y）
```

关键指令（原厂 ELF 的 TA 虚拟地址）：

```text
0xa31d8  BL 0x116c28              // 生成 P-256 私钥标量和公钥点
0xa31ec  BL 0x116a28              // EC key 一致性检查
0xa32ac  MOV x1, x25              // x25 = 本地 KeymasterBlob 输出结构
0xa32b4  BL 0xa79d0                // 序列化 EVP_PKEY -> KeymasterBlob
0xa32b8  LDR x8, [sp,#0x30]        // 原始返回后的第一条指令
```

`0xa79d0` 的 EC 分支先取得私钥材料指针/长度，然后在 `0xa7aa4` 通过 `memcpy` 写入输出 blob。它与 AOSP `EvpKeyToKeyMaterial` 的 `i2d_PrivateKey` 语义一致：这里是 DER/KeymasterBlob 边界，**不是任意 32 字节窗口**。`0xa7b88` 紧邻 `GenerateRkpKey GetEcdsa256KeyFromCert` 语义，只负责证书/对象公钥 X/Y，不能当 scalar 或 CDI seed。

### 2.1 真正的最小观测点

在 `BL 0xa79d0` 返回后、进入 CreateKeyBlob 之前，`x25` 指向的 `(data, data_length)` 才是本把活动 P-256 私钥材料的确定性出口候选。正确诊断记录固定为 0x100 字节：

```text
0x00..0x07  magic = 0x4B37304445523100（小端）
0x08..0x0f  DER 长度（小端，1..0xf0）
0x10..      DER 私钥材料（最多 0xf0 字节）
```

导出后必须先解析为未加密 P-256 私钥，再用同一次 keygen 返回的 `MacedPublicKey` 做 X/Y 逐字节比较；否则只算诊断字节，不能算 IDC 或赛事私钥。

## 3. CSRv3/Binder 边界与主机可见对象

当前活动 CSRv3 入口为：

```text
command dispatcher 0xCB31C (+0x8c)
  -> GenerateCsr 0x626C8
       -> 0x925C8（keysToSign/长度/MAC 对象校验）
       -> 0x94D08（COSE_Mac0 组装）
       -> 0x62CC8（MiTEE 远程配置上下文函数表）
       -> 0x62DDC -> 0x91A40 -> 0x958D8（DICE 条目）
       -> 0x63498 / 0x635A8（vector append/copy）
       -> Binder byte[] CSR
```

主机 Binder 输入只有：`keysToSign_count`、每把 119 字节 `MacedPublicKey` 和 challenge（32 字节以内）；返回一个 CSR byte[]。保存的原生证据为：

| 对象 | 长度 | SHA-256/结论 |
|---|---:|---|
| CSRv3 | 2614 字节 | `cb3dd32fab44899aa9e912af348e30a2e82fed649bac6b5dad047d40f191d51e` |
| challenge | 32 字节 | `5a20fdfa62e77ab6b49a23093396a578cc769381ffc1d079361825ebf4f29900` |
| MacedPublicKey | 119 字节 | `cc5025fffaa8696e6dbe085988e851f31591629c78b86c4b7407ff8fd95db45d` |
| privateKeyHandle | 275 字节 | `ac9ea690b6383af4717fcce3a9f2eb7c0b00f8683c89c696263646aa54d2560e`；opaque，不是私钥 |

`0x92b14..0x92b24` 和 `0x93918..0x93928` 的 0x20 检查由 `0x1003d8` 完成逐字节 XOR/OR 常量时间比较；`0x94d08` 组装 COSE_Mac0。`0x63498/0x635a8` 只是把已经生成的字节复制到返回 vector。活动入口没有直接 `BL 0xda520`；旧 `P256KeypairFromCDI` wrapper 不能套到当前 CSRv3。

独立验证已确认：

```text
UDS SPKI                         d1a3f13b9fae014e1816a988fe4f611c320f315cc1252e366695f76c63bea3c9
CDI leaf SPKI                    0684d469c8afecf9d1a7a86cfc67e4996f2712d5edfcfed80745eeb105b1130b
KeysToSign/Maced leaf SPKI       a7a7555e392b7cd416c89dcaf9b1710fe6cb04e7bd153e0437ed3cb18c0c6cd1
DICE signatures                  5/5 PASS
outer CSR signature              PASS
challenge and Maced binding      PASS
```

这些签名证明私钥在 TEE 中被消费；它们不把 CDI/UDS 私钥交给主机。

## 4. `google-rkp-sw` 的确切核心参数

仓库 `third_party/google-rkp-sw/rkp_sw.py` 的 `resolve_seed()` 只接受：

* 恰好 32 字节 raw `CDI_Leaf` seed；或
* 64 个十六进制字符表示的同一 seed。

P-256 `DeviceKeys` 随后执行 `int.from_bytes(seed, 'big') % P256_ORDER`，并用该 scalar 生成 DICE/CSR 签名键。`keybox`/`provision` 另生成 EC attestation key，将待签私钥以 `key_00/private_key_pkcs8.pem` 保存，再提交 `signCertificates`；只有返回叶证书公钥与该主机私钥公钥匹配才会标记 complete。

所以以下对象全部不满足 `resolve_seed()` 或最终私钥门禁：

* 275 字节 KeyMint opaque handle；
* 119 字节 MacedPublicKey；
* EEK、公钥、MAC、签名或 ProtectedData；
* CSR/供应数据中的任意 32 字节窗口；
* 86f623 的 FID/FF06（静态语义为 `cpu_fid` 派生/编码）。

已有离线复核：13 个定向 K70E 文件、重复来源共 2686 个 32 字节窗口（去重 1864），以及 45 份 MacedPublicKey（40 个唯一公钥），在直接 scalar 和 Open-DICE 两套门控中均为 0 命中；对 1142 个保存候选文件的未加密 P-256 DER 扫描也是 0 命中。

```text

0x62320 -> 0x141500
```


## 8. Fenrir 和“通用 IDC”边界

Fenrir/LK 只影响启动链、AVB 或锁状态，不会提供 `CDI_Leaf` seed，也不会把 TEE 私钥变成主机私钥。静态证据没有显示使用 Fenrir 能缩短上述四项门禁；相反，它会扩大变砖面。当前静态方案不需要 Fenrir。

Nothing 成功案例证明的是“逐把 P-256 private scalar 与同把公钥匹配，再由 Google HTTP 200 证明”的方法；Nothing 的 scalar 不能直接当作 K70E 的 CDI seed、通用 IDC 或 K70E 证书私钥。
