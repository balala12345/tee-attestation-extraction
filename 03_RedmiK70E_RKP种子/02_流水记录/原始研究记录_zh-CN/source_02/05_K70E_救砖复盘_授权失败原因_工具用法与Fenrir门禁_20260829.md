## 一、黑屏/卡 Logo 的原因

此前写入 `lk_a` 的重组镜像不是有效的 Fenrir 产物：`bl2_ext` 比原镜像多 80 字节，随后被截断为 16 MiB。LK 启动链被截断后，设备无法完成正常启动，表现为黑屏、卡 Logo 或只能进入恢复菜单。

这不是基带、userdata 或 BL 锁状态本身造成的故障。原始启动链备份仍在，目标分区也明确是 `lk_a`。

## 二、修复原理与实际工具链

修复只做一件事：在受保护的 MediaTek BROM 中完成 SLA 授权，上传与 `flash.xml` 匹配的 DA，然后以 Download Only 模式把原始 `lk_a` 镜像写回 `lk_a`。没有执行格式化、擦除、efuse、RPMB、userdata、`seccfg` 或 bootloader lock。

本次实际链路：

1. 断开 USB，长按电源完全断电；按住音量上+下插 USB，取得真正 BROM（`A0→5F`）。
2. 使用改版 SP Flash Tool V6、`auth_sv6.auth` 和外部授权响应完成 SLA。
3. `flash.xml` 的 `<dagent>DA_BR.bin</dagent>` 提供 DA；console XML 使用 `conn_stage="2nd DA"`，`com_port_name=""`。
4. console XML 的 `flash_list` 只列出 `lk_a`。
5. DA mode 建立后，`lk_a` 传输进度达到 100%，命令和进程退出码均为成功。

## 三、三次授权尝试为什么失败/成功

“授权卡”不是万能 DA 私钥；它是针对当前 BROM challenge 生成一次响应的外部服务。每次重新进入 BROM、重新发送 `E3` 都会产生新的 challenge，旧响应不能跨 challenge 复用。

| 尝试 | 可证现象 | 真正原因 | 是否写分区 |
|---|---|---|---|
| 第一次 | BROM 握手后打开中文路径的 auth 文件失败，日志出现 `URI File NOT FOUND` | Windows 路径含中文，工具内部 URI/编码解析失败；认证文件本身未被正确打开 | 否 |
| 第二次 | ASCII auth 路径可打开，challenge/授权响应返回；随后报 `No such node (brom.version)` | console XML 仍使用 `conn_stage="brom"`，与该 V6 console 的 DA 阶段不匹配；这是配置状态机错误，不是设备身份拒绝 | 否 |
| 第三次 | `conn_stage="2nd DA"`、空 COM 端口、无非法 `<da-file>` 节点；SLA、DA、写入全部成功 | 使用了与内置 schema 和 `flash.xml` 一致的配置 | 仅 `lk_a` |

期间还出现过一次配置修订错误：把 `<da-file>` 加入 console XML。该版本被工具内置 schema 直接拒绝（`Element da-file is not defined`），因此没有连接设备，也不应消耗授权。DA 路径应由 `flash.xml` 的 `<dagent>` 提供。

说明：本表按本机日志记录的是三次“尝试/会话”及其技术结果；本地日志不能证明第三方服务端是否对某次失败扣除了卡次数。能确定的是，旧响应不能跨 challenge 复用，最终成功会话只对应最后一次 `E3` challenge。

## 四、以后正确使用 V6 工具的固定流程

### 4.1 运行前

- 只使用 ASCII 路径，例如 `D:\duchamp_recovery\auth_sv6.auth`。
- 校验 `auth_sv6.auth`、`flash.xml`、`DA_BR.bin` 和原始 `lk_a` 的哈希。
- 打开 XML 前先确认 `flash_list` 只有目标分区；本任务只能是 `lk_a`。
- 保持 Download Only，Auto Reboot 关闭。
- 不要在设备已进 BROM 后反复重启 SPFT；每次重启都可能产生新 challenge。

### 4.2 XML 规则

该版本 SP Flash Tool 的内置 schema 与网上示例不同：

- `connect-args` 使用 `conn_stage="2nd DA"`；
- `com_port_name` 留空，让工具自动扫描；
- 子节点顺序为 `flash-xml`、`auth-file`、`cert-file`；
- 不要添加 `<da-file>`，即使某些旧模板有该节点；
- DA 路径只放在 `flash.xml` 的 `<dagent>` 中。

### 4.3 授权窗口规则

只在日志确认 `A0→5F`、auth 文件已打开并出现当前 `E3` challenge 后提交授权。窗口显示成功后不要重复点击；等待 SPFT 日志出现 `enter DA mode successed`。若失败，先读取最新 `QT_FLASH_TOOL_V6.log` 和 `host_0.log`，不要盲目再买/再提交。

### 4.4 完成后

- 检查退出码为 `0`，日志明确列出 `lk_a [1/1]` 和 100%。
- 本次 XML 未包含自动重启；结束后拔 USB，再长按电源启动。
- 如需 readback，必须另开只读配置并重新授权，不能把上一次 challenge 的响应当作新会话响应。

## 五、绝对避坑清单

- 禁止 `fastboot flashing lock`、`fastboot oem lock`、MiFlash `clean all and lock`。
- 禁止刷 `preloader`、`seccfg`、`proinfo`、`persist`、`nvram`、`nvdata`、`efuse`、`RPMB`、`userdata`。
- 禁止把上游旧 `duchamp.bin` 或自行截断/拼接的 LK 当作 Fenrir 补丁。
- 禁止跨设备、跨 slot、跨 challenge 混用镜像、auth、challenge 或日志。
- 禁止把“授权成功”误认为“已写入”；必须以 DA mode、目标分区和 100% 进度日志为准。
- 禁止在没有原始备份和哈希的情况下尝试 Fenrir 刷写。

## 六、Fenrir 复现的下一道门禁

本次 `lk_a` 已恢复原版，设备刚恢复到 Logo，尚未证明 Fenrir 可复现。下一步先做只读采集：确认系统能启动、保存当前 slot/`ro.boot.verifiedbootstate`/`ro.boot.flash.locked`、备份当前 `lk_a`，并核对 SHA-256 仍为原版值。

Fenrir 复现必须遵守以下顺序：

1. 在电脑上静态运行 `fenrir` 的 duchamp `PatchStage`，只对原版 LK 做匹配/干运行，不生成刷写镜像。
2. 对照 `liblk` 版本、原始 offset 和补丁模式；任何长度变化、段截断或签名区域变化都停止。
3. 先保存完整输入、工具版本、命令行和输出哈希，再由用户明确确认是否进入设备侧实验。
4. 设备侧若要测试，只允许可恢复的临时/内存路径；绝不先写 `lk_a`，绝不执行 lock 或全刷。

在上述只读门禁通过前，不再消耗授权卡，也不进行新的 BROM 写入。Fenrir 复现与 RKP 证书签发是两条独立链路，不能用一次成功的 `lk_a` 恢复推断 Fenrir 或 RKP 结果。
