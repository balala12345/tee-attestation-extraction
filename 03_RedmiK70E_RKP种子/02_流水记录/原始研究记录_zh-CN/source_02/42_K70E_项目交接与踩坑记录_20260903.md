## 1. 赛事目标（不变）

从 K70E（Redmi K70E / `duchamp` / `<DEVICE_SERIAL>` / 序列号 `<DEVICE_SERIAL>`）取得 RKP 身份材料，用 `google-rkp-sw` 生成合法请求，取得 Google/主办方沙箱签发的真实证书，保存私钥+请求+响应+证书链，解析有效期和近 30 天签发数量。

**交付三件套（缺一不可）：**

```text
1. 同钥主机可读 P-256 私钥（原始 scalar / PKCS#8 / 未加密 DER）
2. Google 叶证书（HTTP 200 + 原始请求/响应）
3. 私钥公钥 = 同次 MacedPublicKey = 叶证书 SPKI（逐字节相等）
```

**唯一验收标准：**

```text
主机可读 P-256 私钥
→ 公钥与同次 MacedPublicKey 逐字节相等
→ Google HTTP 200 叶证书 SPKI 与该公钥相等
```

三项同时出现才算进展。只出现 CSR 签名成功、HTTP 200、275B opaque blob、32B 窗口、google_count 都**不算**。

用户明确记得：**一开始刷社区版带 Fenrir 的 HyperOS 打不开系统，提示系统没解锁校验没过；然后执行了一个 BL 解锁命令（有进度条），之后解锁了、root 了、也进 HyperOS 了。**

- 8-28~8-31 期间：`unlocked: yes` / `secure: no`、seccfg=`3`（UNLOCKED）、`verifiedbootstate=orange`、`flash.locked=0`、KernelSU 3.2.5 root

**结论：解锁状态是真实的，不是记错；当前锁定是 9/2~9/3 恢复流程后的状态。** 具体原因待确认（可能是恢复时重锁，或之前依赖 KernelSU 注入显示）。

**重要**：`lock_state` 是持久化的，只有刷 `seccfg` 分区才改变；fastboot / flash 操作**不会**自动锁。所以当前 locked 更可能是"之前就锁，之前显示 unlocked 是 KernelSU 注入伪装"或者"恢复流程中写回了锁状态"。

## 7. 为什么之前工作举步维艰（技术根因）

### 7.1 K70E 与 xaga 的本质区别

```text
xaga (11T Pro) 成功路径:
  bad_io_uring 竞态提权 (纯用户态内核漏洞, 不碰 BL)
  → root + capability + SELinux Permissive
  → Fenrir 补丁 LK (取消 bl2_ext 校验)   ← xaga 上可用
  → 补丁 TEE (TA 验签错误分支 NOP)
  → bind mount 补丁 TA (替换 EEK 根为本地持有)
  → 冷启动 → 采集 DeviceInfo/keysToSignMac/ProtectedData
  → 本地 EEK 解密 → BCC + SignedMac + 稳定 Device Key

K70E 现状:
  Fenrir LK        → 二进制级证明不可用 (sbcen_unlock=2 → img_auth=1 forever)
  tee_a 补丁       → 已验证被拒 (2 次)
  所以 ta-mgr patch 点找到也没用 (需要 Fenrir LK 才能运行 patched TEE)
```

**xaga 的成功不是靠解锁，是靠用户态竞态 root + Fenrir。K70E 缺的是 Fenrir 可用性。**

### 7.2 K70E 与 Nothing 的区别

- Nothing 用 Trustonic t-base MCLF（trustlet 验签可旁路）
- K70E 用 MiTEE / Mitee KeyMint，TA 管理和认证边界不同
- **不能类比**，Nothing/MCLF 路径不可移植

## 8. 剩余可行路径（按优先级）

### 路径 A：xaga 同款（用户态竞态 root，不碰 Secure Boot）

```text
判断 K70E 内核是否适用 bad_io_uring 竞态提权
→ 若可用: 拿 root + SELinux Permissive
→ 绕 TA 验签（ta-mgr patch 已定位）
→ 替换 vendor 里 RKP TA 的 EEK 根为主机本地 EEK 根
→ 冷启动 → 采集 ProtectedData → 本地 EEK 解密 → 得到 BCC/Device Key
→ 验证私钥 = MacedPublicKey = 叶证书 SPKI
```

**优点**：纯用户态，不碰 Secure Boot/带熔丝分区，失败最多重启不硬砖
**关键门禁**：`bad_io_uring` 竞态 root 在 K70E 上是否可行（从未试过）
**K70E 的 RKP TA 路径**：`/vendor/mitee/ta/dba51a17-0563-11e7-93b16fa7b0071a51.ta`（vendor = AVB 保护，不是 Secure Boot）

### 路径 B：官方解锁 BL → 竞态 root → AVB flags=3 → vendor TA 替换

```text
重新解锁 BL（用户之前解锁成功过，方法待找）
→ root（坏扇区 io_uring 竞态）或 KernelSU
→ vbmeta flags=3（AVB 顶层 VERIFICATION_DISABLED，停止遍历 descriptor）
→ 替换 /vendor TA（AVB 保护，不是 Secure Boot）
→ 冷启动采集
```

**前提**：能重新解锁（曾成功）、能 root（竞态或 KernelSU）
**注意**：官方解锁可能有 168h 等待/账户绑定限制

### 路径 C：AVB 层 Magisk/init_boot 补丁（已评估有限）

```text
只动 boot/init_boot/vbmeta（AVB 分区），不碰 Secure Boot
→ Magisk / init_boot patch → root shell
→ 但 v5 现场已证明：root shell 不能进入 TEE，CSRv3 链路无主机可见私钥出口
→ 预期收益有限
```

## 9. 下一步建议（给下一个操作者）

1. **确认 K70E 当前内核版本**，评估 `bad_io_uring` 竞态 root 可行性（纯只读，零风险）
2. **找到当初的 BL 解锁工具/命令**（用户记忆：进度条解锁），确认能否重新解锁
3. **若可 root + 解锁**：优先走路径 A（xaga 同款），不碰 Secure Boot
4. **除非拿到芯片级密钥或 LK 层放行，不要再碰 tee_a**
5. 每次操作前核对：目标分区、源文件哈希、边界授权；操作后验证 `sys.boot_completed=1`
