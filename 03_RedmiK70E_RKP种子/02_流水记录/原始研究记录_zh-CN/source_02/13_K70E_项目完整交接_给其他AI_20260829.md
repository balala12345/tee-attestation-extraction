## 1. 题目目标与当前结论

CTF 目标是：从 Redmi K70E（`duchamp`）取得与设备身份对应的 RKP 材料，使用 `google-rkp-sw` 或等价实现生成请求，取得 Google/主办方沙箱签发的证书，保存私钥和证书，解析有效期，并记录题目要求的本月签发次数。

截至本交接时，结论分成两个层次，不能混为一谈：

1. **设备侧 RKP 已被证明可用。** 原厂 Mitee KeyMint v3 的 `GenerateCertificateRequestV2`/CSRv3 调用成功；工作区还保存了系统 `rkpd` 已经取得的 12 组真实 Google 证书链。叶证书签发者为 `CN=Droid CA3,O=Google LLC`，链根为 Google `Key Attestation CA1`。这证明“这台设备可以走原生 CSRv3 并取得 Google 证书”。
2. **完全脱机的“32 字节 IDC → google-rkp-sw --seed”材料没有取得。** 通过一次完整 V2 调用的 Binder 边界、原厂 TA 活动入口、厂商安全上下文、DICE 结果对象和独立验证结果闭合复核后，对已观察调用链的最终二选一结论是：UDS/CDI 私密材料只在 TEE 内被派生/消费，主机只见到公钥、签名、MAC、opaque handle 和最终 CSR 字节；没有发现能独立重建同一 UDS SPKI 的主机可见私密出口。

因此，当前**不能**声称已经提取了可供 `google-rkp-sw --seed` 使用的 IDC，也**没有**在本轮发起新的 Google/签发端请求。历史证书不能冒充本轮新签发，`google_count` 也不能冒充 Google 后端自然月签发总数。

## 4. CSRv3 协议边界（不要误套 legacy/xaga）

K70E 是 Mitee `IRemotelyProvisionedComponent` v3，调用的是 `generateCertificateRequestV2`，不是 xaga 的 legacy v1，也不能直接套 Nothing 项目的 32 字节 scalar 经验。

主机 Binder 客户端：
`<PROJECT_ROOT>/<DEVICE_WORKSPACE>/02_脚本与补丁/rkp_binder_csr_v2_client.cpp`

关键边界：

1. Binder dispatcher：`0xCB31C + 0x8c`，进入活动 `GenerateCsr` `0x626C8`；
2. 主机发送 `keysToSign` 数量、每个 119 字节 `MacedPublicKey` 和 0..64 字节 challenge；
3. TA 返回单个 CSR byte array，客户端原样保存；
4. Binder 参数中没有 UDS/CDI seed、DICE 私钥或 IDC 槽位；
5. 275 字节 `privateKeyHandle` 只用于 KeyMint 后续操作，是不透明句柄。

AOSP 官方接口也明确区分：V2 以 `keysToSign` 和 `challenge` 输入，返回 CSR；legacy 接口才分开返回 `DeviceInfo`、`ProtectedData` 和 `keysToSignMac`。参考：[AOSP AndroidRemotelyProvisionedComponentDevice.cpp](https://android.googlesource.com/platform/system/keymaster/+/refs/heads/master/ng/AndroidRemotelyProvisionedComponentDevice.cpp)。CSRv3 数据结构和 DICE/UDS 链定义见：[AOSP generateCertificateRequestV2.cddl](https://android.googlesource.com/platform/hardware/interfaces/+/04d2ed4ff01dcfb62d8e6fce492d315b3749e3cc/security/rkp/aidl/android/hardware/security/keymint/generateCertificateRequestV2.cddl)。

## 5. 原厂 TA 活动调用链与私密边界

对原始 ELF 的 AArch64 静态反汇编得到以下闭合路径（偏移均为 ELF 内偏移，不是源码行号）：

```text
Binder dispatcher 0xCB31C (+0x8c)
  -> GenerateCsr 0x626C8
     -> 0x925C8      输入 key / 中间对象检查
        -> 0x92E18 / 0x92F60 / 0x93208
        -> 0x94D08   COSE_Mac0 相关对象
     -> 0x62CC8      通过上下文函数表间接调用厂商安全接口
     -> 0x62DCC -> 0xF5DE0
        -> 0x12CD60 / 0xF2680 / 0xF18D0 / 0xF1430
     -> 0x62DDC -> 0x91A40 -> 0x958D8
        -> DICE 条目解析/结果对象
     -> 0x63498 / 0x635A8
        -> vector append/copy
     -> Binder CSR byte[]
```

### 5.1 已确认的各阶段语义

| 阶段 | 观察到的输入/输出 | 能否作为 IDC 出口 |
|---|---|---|
| `0x925C8` 输入检查 | COSE 对象、算法/曲线/长度；`0x92B14–0x92B24` 仅做 0x20 字节常量时间比较 | 否；比较不是复制/导出 |
| `0x94D08` | 分配约 0x20 字节对象并写入 `MAC0` 标记，组装 COSE_Mac0 | 否；是 MAC/公钥完整性对象 |
| `0x62DCC -> 0xF5DE0` | TA 内部两个 32 字节临时对象，调用多个内部 helper | 当前没有写入 Binder reply 的边；不能据长度命名 IDC |
| `0x62CC8` 上下文表 `0x148390` | 表项落在 `0xBBF40/0xBC410/0xBE710/0xBEB18/0xBEC48/0xBEC98`，涉及持久化、DeviceInfo、MAC、SignedMac、ProtectedData 包装 | 返回状态/公开对象/受限对象，未见 raw seed 复制 |
| `0x91A40 -> 0x958D8` | DICE 条目容器解析和结果整理 | 只把公钥、payload、签名放入 CSR；私钥作为签名上下文被消费 |
| `0x63498/0x635A8` | `memcpy`/vector append 已生成字节 | 只能说明 CSR 组装，不能推断秘密来源 |

关键补充：旧字符串 `DiceSign`、`DiceCoseSignAndEncodeSign1`、`DiceKeypairFromCDI` 的交叉引用主要落在旧辅助路径（例如 `0xD87F0 -> 0xDA520`），活动 V2 的 `0x626C8` 直接边没有到旧 `P256KeypairFromCDI` wrapper。不能把旧 legacy 窗口或诊断 TA 暂存区当成当前 CSRv3 IDC。

### 5.2 最终二选一结论

对“已保存的这一次完整 `GenerateCertificateRequestV2` 调用链”，选择：

> **私密 UDS/CDI 材料始终留在 TEE 内，当前 Binder/CSR 结果没有主机可见 IDC 出口。**

这不是“设备永远没有调试出口”的泛化断言；它是对 stock TA ELF、实际 Binder 输入/输出和独立验证结果的限定结论。若后续要推翻它，必须提供新的、可复现的主机可见材料，并用独立算法重建上述 UDS SPKI；仅有 32 字节长度、与公钥/MAC/签名/opaque blob 相似，均不够。

## 6. 已拒绝的 32 字节候选和原因

工作区曾出现以下候选，均没有通过“独立 P-256 派生 → 重建 UDS SPKI”门控：

1. 诊断 TA 固定地址 `0x158968` 的 32 字节值：SHA-256 `a148ec407f21f6e0cb845577a1b26ab1339fcdb14e009a9dd509ca7fa35cd2c5`；派生 SPKI SHA-256 `7a827c37bf3cf9b7d185fbbf3cde87de652c67d19b6be36f4200e4b5ce84f147`，不等于原生 UDS 基线 `d1a3f13b9fae014e1816a988fe4f611c320f315cc1252e366695f76c63bea3c9`；
2. 诊断 TA `0x158900` 起的 256 字节窗口：225 个重叠 32 字节候选，`match_count=0`；窗口 SHA-256 `f4ca31074b47e4dfecf797e3721c1ab598b212920948db24d968c42865108917`；
3. 活跃种子诊断第三轮 `private_blob+0x20` 预期标记未出现（实测 `06df138b`），窗口 `[0:256]` 225 个候选 `match_count=0`；
4. 设备固定 EEK 公钥 X、COSE MAC tag、返回 vector 的临时 32 字节缓冲、275 字节 opaque private blob：语义或独立重建均不成立。

- `03_提取结果/K70E_P256_CDI实机输出缓冲区采集_20260829_第三轮/manifest.json`（SHA-256 `61761d433a4f869ce06c35971e49b8ad5f123a8455ae1ff70a43e8daac6ea665`）；

结论是“这些候选失败”，不是“设备没有 IDC”；在完整 V2 调用链闭合后，正式验收才进一步得出“该调用链的私密材料不出 TEE”。

## 10. 给下一位 AI 的明确工作边界

### 允许且有价值

- 先校验本文、`csr_v3_call_chain_evidence.json`、原始 CSR 和独立报告的 SHA-256；
- 继续对原厂 TA ELF 做静态反汇编/交叉引用，重点解释 `0x62CC8` 的间接表项和 `0xF5DE0` 下游，但不得把猜测写成导出事实；
- 若找到新的主机可见候选，必须用独立实现从候选重建 UDS SPKI，并与 `d1a3f13b...` 完全匹配后才可命名为 IDC；
- 若题目需要真正新证书，优先使用主办方提供的沙箱签发端或明确的测试身份；保存原始响应后再解析链、OID、notBefore/notAfter 和后端明确返回的计数。

### 禁止重复

- 不要继续扫描任意 32 字节窗口；
- 不要把 `MacedPublicKey`、EEK、公钥、MAC、签名、ProtectedData、275 字节 opaque blob 或比较缓冲区改名为 IDC；
- 不要把 HBK/Device Key Seed 直接塞进 `google-rkp-sw --seed`；
- 不要把 xaga legacy、Nothing A142 或 CSRv3 混成同一协议；
- 不要把主机自生成/自解密的材料当作 TA 原生输出；
- 不要再刷 LK、替换 TA、重启 TEE 或尝试锁 BL，除非另有完整备份和明确的恢复方案；
- 不要依据 HTTP `Crypto error` 或客户端 `google_count` 推断 Google 身份拒绝或后端月度签发量；
- 不要公开或复制私钥原文、卡密和账号口令。
