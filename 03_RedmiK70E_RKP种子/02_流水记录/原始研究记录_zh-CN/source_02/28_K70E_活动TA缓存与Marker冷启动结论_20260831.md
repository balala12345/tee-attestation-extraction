## 已验证的静态调用链

```text
GenerateRkpKey 0xc94d8
  -> 0x61960
  -> 0x610e8 (GenerateKey 虚调用)
  -> 0xa2fd0 (KeyFactory::GenerateKey)
  -> 0x116c28 (EC_KEY_generate_key)
  -> 0xa79d0 (EvpKeyToKeyMaterial / DER 序列化)
  -> 0xa32b8 (返回后，x25 指向 KeymasterBlob data,length)
```

`0x62358` 位于返回向量整理逻辑：原指令是 `ldr q0,[x8]; str q0,[x22]; stp xzr,xzr,[x8]`，其中 `x22=x25+0x10`，对应 Binder 返回结构中的另一向量字段。v3 补丁在该点保留原指令，再把已在 `0xa32b8` 捕获的 DER 复制到该向量；第二向量赋值 `0x62320` 已恢复为原厂指令。

## Marker 运行结果与解释

1. **进系统后 bind marker + 重启 KeyMint**：返回仍为 275 字节 opaque blob，无 `c7c7`。这只能说明安全世界继续使用已缓存的原厂 TA；不能证明 `0xa32b8` 或 `0x62358` 未执行。
2. **停止并重启 tee-supplicant 后再 bind**：服务进入 `restarting`，随后已卸载 bind 并恢复原厂哈希；普通重启后服务恢复正常。该方式不再重复。
3. **早期 bind marker + 普通 `adb reboot`**：USB 未重新枚举。已有历史证据表明安全世界 TA 实例在普通软件重启后仍保留，必须真正断电/上电才能清空缓存；当前模块的 `early_bind.sh` 会在启动时写入 `disable`，下一次启动回到原厂。

## 下一次唯一运行时步骤

在设备可物理操作时：

1. 先确认手机进入 fastboot 或 Recovery，等待模块 `disable` 生效并回到原厂系统；只读核对原厂 TA 哈希。
2. 重新 armed **v3 vector TA**（不是 marker），执行一次真正冷启动/断电上电；不要使用 `adb reboot`。
3. 启动后从 metadata 取一次 keygen 输出。只有同时满足诊断 magic、DER 结构合法、DER 公钥 X/Y 与同一调用的 MacedPublicKey 完全相等，才进入 native CSR 独立验证和 `google-rkp-sw` 提交。
4. 任一门禁失败立即卸载/禁用模块并恢复原厂；不得把 opaque blob、CSR 签名成功或现有证书当成私钥交付物。

## retry-safe 部署修正

上一轮 v3 `.armed` 在 early-init 被改为 `.inuse` 后没有生成新的 `bind_success`，随后可见 TA 仍是原厂；这表明 bind 发生在 `/vendor` 可用之前并失败，而不是 v3 已执行。已准备 [`early_bind_retry_v2_20260831.sh`](../02_脚本与补丁/early_bind_retry_v2_20260831.sh)，逻辑是在 bind 失败时恢复 `.armed`，让 post-fs 触发器再次尝试；旧脚本已在设备 metadata 备份。当前 v3 `.armed` 载荷哈希为 `5a3e5b19…1ec2d80`，仍未宣称加载成功。

## 2026-08-31 namespace 复核与修正

本次真正 `PowerKey` 启动后的只读核对结果为：`tee-supplicant=running`、
`vendor.keymint-mitee=running`，但 `/vendor/mitee/ta/dba51...ta` 仍为原厂哈希
`facdfe3d8cb546acbbb4dc233b139a4dfd65f01e4791bbc26c474eb2eb0a3f32`；早期
keygen 仍只有 275 字节 opaque blob 和 119 字节 MacedPublicKey，没有诊断
magic/DER。该结果不能再归因于 TEE 缓存。

进一步读取 mount namespace 得到确定原因：`init`/`adbd` 在
`mnt:[4026534075]`，而 `tee-supplicant`（PID 599）在独立的
`mnt:[4026531841]`。原有 `early_bind.sh` 在前者执行，文件级 bind 成功标记
并不代表 TA 管理器读取到 v3。一次可逆验证在 PID 599 的 namespace 执行：

```text
nsenter -t 599 -m -- mount --bind <v3.ta> /vendor/mitee/ta/dba51...ta
tee namespace hash = 5a3e5b19d88950fa0b018425479946394c08948691187e990bf8971241ec2d80
umount 后两 namespace 均恢复原厂哈希
```

因此新增 [`early_bind_tee_ns_v3_20260831.sh`](../02_脚本与补丁/early_bind_tee_ns_v3_20260831.sh)，
在 `post-fs` 等待 `tee-supplicant` PID，使用 `nsenter -t <pid> -m` bind，
并在同一 namespace 核对 v3 哈希；early-init 只保留 `.armed`，避免等待导致
`on fs` 死锁。配套 rc 为
[`00_k70e_bcc_seed_diag_tee_ns.rc`](../02_脚本与补丁/00_k70e_bcc_seed_diag_tee_ns.rc)。
两文件仅写 metadata/module 配置，不刷写分区。

为恢复一次错误的手动服务重启，曾临时停止 `tee-supplicant`；由于运行态
`/dev/kmsg` 无法恢复到原厂组属，服务进入 `restarting`。随后已执行一次普通
`adb reboot`，当前服务和原厂 TA 均恢复正常；该轮没有留下活动 bind。

## 2026-08-31 post-fs-data 时序修正

冷启动日志显示 `post-fs` 绑定发生在 `INIT:Mount_START --late`（约 5.973 秒）之前；
后续 late vendor mount 会覆盖 `/vendor`，因此即使 `nsenter` 在 tee-supplicant
命名空间内返回成功，运行中的 TA 仍恢复为原厂哈希。现已将绑定和早期 keygen 触发器
移到 `post-fs-data`（约 6.238 秒以后），并重新部署 active init rc。该修正只写
KernelSU metadata/module 配置，不触碰任何分区。下一次启动需再次改名旧
`bind_success_tee_ns_20260831` 标记后进行物理冷启动；监测器只在 tee 命名空间哈希为
v3 时调用主机采集器，采集器自身在 magic、DER/P-256、同把 Maced X/Y、原生 CSR
独立验证和 Google HTTP 200/叶公钥匹配全部通过后才保存/提交最终产物。

## initrc 备份文件门禁

KernelSU 会把活动模块 `initrc/` 目录中所有以 `.rc` 结尾的文件拼接进
`modules.rc`。因此回滚副本不得保留 `.rc` 后缀；设备上的
`00_k70e_bcc_seed_diag_before_tee_ns_v3_20260831.rc` 与
`..._v5_20260831.rc` 已在下一轮启动前改名为非 `.rc` 备份（内容保留），
确保只有 post-fs-data 版本的活动 rc 会被解析。
