## 4. 阶段一：只读识别 Recovery

### 4.1 先唯一识别设备

在实际操作主机上使用该主机已验 hash 的 Fastboot。下面命令只是教程，不代表本轮已执行：

```sh
fastboot devices -l
fastboot -s <DEVICE_SERIAL> getvar serialno
fastboot -s <DEVICE_SERIAL> getvar product
fastboot -s <DEVICE_SERIAL> getvar current-slot
fastboot -s <DEVICE_SERIAL> getvar is-userspace

```

门禁：只能有一个目标，且 serial/product/slot 必须分别是 `<DEVICE_SERIAL>`、`duchamp`、`a`，`is-userspace=no`。空清单、多个设备、错误序列号、userspace Fastboot 均停止。Fastboot 的正常 `getvar` 值通常输出到 stderr；必须分别保留 stdout、stderr 和退出码。

### 4.2 先辨认上次 Recovery 请求后的真实状态

暂停前已经发过一次串号绑定的 `reboot recovery`，所以恢复时不能把它当作
默认下一步。必须先记录手机屏幕和 fresh USB inventory。只有屏幕/枚举明确
表明设备仍是唯一目标 Fastboot，且离线审计确认确有必要时，才可重新评估
是否再发一次：

```sh
fastboot -s <DEVICE_SERIAL> reboot recovery
```

该命令只请求切换启动模式，不写分区。即便重新评估后执行且返回 `OKAY`，
仍必须观察手机和 USB，不能宣布 Recovery 已启动。

| 实际表现 | 分类 | 下一步 |
|---|---|---|
| 小米官方 Mi-Recovery 主菜单，含 `Reboot` / `Wipe Data` / `Connect with MIAssistant` | 官方 Recovery 候选 | 不点 Wipe；记录照片、USB VID/PID、菜单版本，进入合法写通道评估 |

## 5. 阶段二：获得合法、可审计的写通道

这里的“合法”仅指：通道真实获得写权限、目标绑定明确、可保存完整证据且不会靠伪造成功状态继续。按优先级选择一个，不得并行试写。

### A. Recovery 已实际启动

如果是 OrangeFox，只有在以下只读门全部成立后，才能把它视为候选临时写通道：

- 唯一 USB/ADB 序列号属于目标 K70E；
- Recovery 身份、版本、启动槽有原始证据；
- `/dev/block/by-name/vendor_boot_a` 和 `init_boot_a` 唯一解析到 UFS LU2，块大小分别是 `0x4000000`、`0x800000`；
- 能先完整只读备份两分区并保存 size/SHA-256；
- 已有专用、测试通过、只允许两个 A 槽目标的 paired restorer；不得手敲 `dd`；
- 两个官方源文件先在主机和 Recovery 端分别验 hash；
- 写后可在不重启的同一 Recovery RAM 会话读回两分区并验 exact hash。

如果是官方 Mi-Recovery，只能使用其官方签名更新/`Connect with MIAssistant` 能力。不要尝试把 raw 镜像伪装成 OTA，不要选择清除数据。

### B. 完整、签名的 CN304 Recovery ROM


### C. 经授权的 BROM -> Auth -> DA 通道

当前 Auth 卡密已耗尽，所以本路现在没有写授权。取得新的明确授权后，也必须从新的 fresh challenge 开始：

```text
BROM/COM 枚举
  -> fresh challenge
  -> challenge 对应的有效 auth response 被设备接受
  -> DA1/DA2 真正进入
  -> 先执行只读 pair readback
  -> 审核读回与 XML
  -> 成对写 A 槽官方 vendor_boot/init_boot
  -> 同会话读回并验 hash
  -> 才允许重启
```

challenge、Auth 文件、DA 进入和分区 IO 是四个不同状态，缺一不可。每次重连 challenge 都失效；旧 response 不得复用。购买/充值第三方授权属于新的付费权限，必须由用户单独决定，AI 不得自行购买。

scatter 中的预期 UFS LU2 几何仅供复核，不能替代 fresh scatter/DA 审计：

```text
vendor_boot_a  offset 0x43800000  length 0x04000000
init_boot_a    offset 0x47800000  length 0x00800000
```

### D. Stock Fastboot

只有 fresh `getvar unlocked=yes` 且完整写权限门通过时，Fastboot 才可能成为写通道。已观测状态是 `unlocked=no, secure=yes`，官方 `init_boot_a` 写入已经被 `No support by lock control` 拒绝，因此当前不能再盲试 `fastboot flash`，更不能用 `oem unlock` 试探。

没有 A/B/C 中任一真实可用通道时，就停在这里；这不是可以靠多点几次按钮突破的步骤。

- 不运行旧 `verify_k70e_cn304_approved_postboot.py` 来生成放行 marker；
- 不手工创建或复制 `POSTBOOT_VERIFIED.json`；
- 必须把官方 pair、根权限策略和测试一起升级；旧 PORTABLE/RECOVERY/HANDOFF
  三份 manifest 保留隔离，不通过改 hash 复活。完成新语义后另建新的
  replacement execution manifests 并重新冻结。

### 7.3 stock-log 权限门

当前 collector 必须通过 profile 固定的 Magisk 路径取得 root，才能读取 `/data/vendor/mitee/mitee.log`、分区 hash 和服务状态；官方 `init_boot` 启动后预计没有该 root。不得把“Android 正常开机”直接接到 zero-key。

下一步工程必须先证明一种不会改变最终批准 DICE 的日志读取方案，或者建立比赛允许、可复算且与批准基线一致的 root 路线。禁止在本恢复中修改 lock state，禁止为了拿 root 重新刷 Magisk/Fenrir 后直接签发。只有新的 stock postboot/capture 合同把访问能力也验证通过，才允许进入下一阶段。

只允许官方 endpoint `https://remoteprovisioning.googleapis.com/v1`。状态顺序必须是：

```text
live stock/offline gate
  -> ATTEMPT
  -> DEVICE_LATCH
  -> NETWORK_STARTED
  -> 一次 core（一次 fetchEekChain POST + 一次 signCertificates POST）
  -> strict audit
  -> SUCCESS 或 BURNED
```

`ATTEMPT` 之后的任何失败均视为本 attempt 已消耗，绝不重试。`NOT_APPROVED` 烧毁该 attempt，但在无 429/quota/abuse/未知网络结果时继续离线找环境差异；只有修复一个可证明的差异并重新过门，才能建立另一独立 controlled attempt。
