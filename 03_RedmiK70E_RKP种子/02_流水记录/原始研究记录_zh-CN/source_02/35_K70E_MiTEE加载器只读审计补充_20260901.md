# K70E MiTEE 加载器只读审计补充

日期：2026-09-01（Asia/Taipei）  
范围：仅分析已保存的 `tee-supplicant`、`keymint-service`、TEE 镜像、原厂 KeyMint TA 和历史日志；不刷写、不重启、不加载 TA、不联网提交，也不包含签名绕过或私钥导出步骤。

## 结论先行

目前没有找到 K70E 上已经被证实的、类似 Nothing/Trustonic 案例的 TA 签名旁路。

可以确认的是：

1. MiTEE 的用户态加载器负责“找文件、读文件、通过 RPC 交给安全世界”；它本身没有看到可关闭签名校验的开关，也没有承担最终签名授权。
2. 最终认证边界在安全世界的 `ta-mgr`/TEE 侧。TEE 镜像中同时存在 `load_from_file`、`authenc`、`signature mismatched` 等相关内容；这只能说明存在认证/完整性处理，不能说明存在可利用旁路。
3. 当前 `tee_a` 与 `gz_a` 是原厂内容，Fenrir 候选 LK 只改变启动链放行范围，不能据此推导 MiTEE 会接受任意修改后的 TA。
4. 工作区没有找到 K70E 专用的工程签名 TA、测试 TEE、测试公钥链或已验证的“忽略 TA 签名”构建。因此不能把文件级 bind、`launch OK` 或一次 Binder 成功解释为“修改 TA 已在安全世界执行”。

这不是“设备永远没有漏洞”的证明，而是“现有证据不足以证明存在同类旁路”。

## 1. 用户态加载器的静态证据

主机副本：

```text
$HOST_TMP_DIR/k70e_live_bins_20260901/tee-supplicant
SHA-256: b797a47ec586bd1dcf73d0ba88eb4f03da7a23026450be327b15c8ac085bce08
```

该文件是 stripped AArch64 ELF。`TEECI_LoadSecureModule`（ELF VA 约 `0x6900`）的可见流程是：

- 检查输入指针、UUID、长度和参数形状；
- 依据 UUID 组成 `/vendor/mitee/ta/<uuid>.ta` 等路径；
- 使用 `fopen`、`fseek`、`ftell`、`fread`、`fclose` 读取文件；
- 通过 `ioctl`/`TEE_IOC_SUPPL_SEND` 把模块数据交给内核和安全世界；
- 失败时返回错误并记录 `TA not found`、`wrong TA path`、`wrong inparameter` 等信息。

对该 ELF 的导入表和字符串没有看到签名库、哈希库、证书验证入口或 `skip/disable/allow unsigned` 一类控制项。`main` 暴露的 `-d` 只是守护进程选项，不是调试认证模式。因此替换路径、改 namespace 或做文件级 bind，都只能影响“主机读到哪一个文件”，不能替代安全世界的授权决定。

## 2. KeyMint 用户态服务的边界

主机副本：

```text
$HOST_TMP_DIR/k70e_live_bins_20260901/keymint-service
SHA-256: 2e04dd29bb8258f048e58d789a99e1c6831a080806403de6686b3a8aba783322
```

其可见职责是 AIDL/Binder、KeyMint 消息编解码和 `TEEC_InitializeContext`/`TEEC_OpenSession`/`TEEC_InvokeCommand` 调用。字符串包含 `GenerateCsrV2Request`、`IRemotelyProvisionedComponent` 和 `Secure hardware access denied` 等正常接口信息；没有发现改变 MiTEE TA 验证策略的分支。它是正常世界胶水层，不是 Nothing 案例中 Trustonic t-base 的等价物。

## 3. 安全世界证据

当前原厂 TEE 镜像：

```text
<PROJECT_ROOT>/<DEVICE_WORKSPACE>/01_设备输入/duchamp_当前启动链只读备份_20260828/tee_a.img
SHA-256: 18227785891a3db4119fb3055ae09bb538a6a8e9ce874876b34d287386eaf21d
```

其中能看到 `ta-mgr`、`load_from_file`、`authenc`、`signature mismatched` 等字符串。历史 MiTEE 日志出现过 `SFS miss`、`SProviderLoad_ta_from_ree`、版本/权限检查和 `launch OK`，但没有一条用户态证据能把这些阶段等同为“修改 TA 的生产签名已经通过”。

原厂 KeyMint TA：

```text
<PROJECT_ROOT>/<DEVICE_WORKSPACE>/01_设备输入/duchamp_Mitee_TA与KeyMint用户态_20260828/ta/dba51a17-0563-11e7-93b16fa7b0071a51.ta
SHA-256: facdfe3d8cb546acbbb4dc233b139a4dfd65f01e4791bbc26c474eb2eb0a3f32
```

TA 中同时存在 `Auth Verification`、`DiceVerify`、`MAC tag mismatch`、`Error MACing RoT`、`Test key in production request`、`P256KeypairFromCDI` 和 `GenerateRkpKey` 等正常生产逻辑与错误路径。这些字符串支持“TA 会做认证和生产/测试区分”，不提供任何绕过结论，也没有出现可直接导出生产私钥的公开接口。

## 4. 与 Nothing 成功案例的差异

Nothing 的成功前提是 Trustonic/t-base 的 MCLF trustlet 验签边界被改变，随后修改后的 KeyMint trustlet 才有机会运行。K70E 使用 MiTEE，现有 Fenrir 包中的 `tee.img`/`gz.img` 有效内容仍与官方镜像一致；因此不能把 Fenrir LK 的生效，等价为 MiTEE TA 验证器已经被旁路。

当前没有以下任何一种可核验物：

- MiTEE/TEE manager 的已签名工程版本；
- 赛事方提供的测试 TA 或测试签名链；
- 明确记录“未签名 TA 被安全世界接受并执行”的 marker 对照；
- 与原厂 TA 冷启动、同一 UUID、同一会话对应的安全世界执行证据。

## 5. 对当前工作的含义

“能把文件放进 `/vendor/mitee/ta/`”和“安全世界接受并执行该文件”是两件事；“TA 能执行”与“会把 CDI/UDS 私密材料交给主机”又是两件事。现有 K70E 记录不能把这三件事合并成一个成功结论。

在没有合法测试固件或测试签名材料前，继续修改加载器、TEE 或 TA 只会扩大变砖和泄露风险，也不能形成可靠的 RKP 证据。安全可继续的工作仅限：

- 对已保存镜像/二进制做只读函数和数据流标注；
- 在模拟器或主办方签名测试 TA 上用固定公开 marker 验证加载链；
- 用原厂 CSRv3 做公钥链、签名和证书库存审计；
- 等待赛事方/厂商提供工程签名测试材料后，再核对“加载成功”这一前置条件。

本轮没有修改设备，也没有生成或保存新的密钥、证书或请求。
