## 1. 调用方法

在 Codex 中明确写：

```text
Use $k70e-rkp-ctf to verify the final K70E google-rkp-sw submission.
```

或中文：

```text
使用 $k70e-rkp-ctf 只读核验 K70E 提交包的 Provisioning Info，并判断 stock 测量环境是否有联网资格。
```

默认行为是只读审计旧包。对 `_2244` 包的正确结果是 FAIL，不会为了“再确认一次”重复刷写、身份捕获、Binder keygen 或 Google signing。

项目根已有维护中的 `SHA256SUMS_PORTABLE.txt`，它同时钉住六入口及其安全敏感依赖；不要把单个 hash 复制到文档里形成会过期的第二份真相。每次使用前先从项目根执行：

```bash
shasum -a 256 -c SHA256SUMS_PORTABLE.txt
```

portable profile v3 把设备参考、工具链和 issuer approval 三个判断域分开：

- `device_reference_id=duchamp-cn304-mitee-exactframe-v1`：只钉固件、TA/TEE/candidate/sidecar 与 Exact 边界；
- `toolchain.allowlist.id=k70e-portable-macos-host-20260906-v2`：钉包含 Provisioning Info 硬门的新 `rkp_sw.py` 及其余执行依赖；旧 v1 仅用于审计历史包。
- `approval_environment`/`network_issuance_allowed`：独立比较认可的 stock DeviceInfo、stock CDI leaf 与五层 DICE 测量，不能由 Exact 构建分类代替。

更新任一域都必须发布新 ID 并独立审计，不能顺带放宽另一域。

## 3. 手工运行离线验证器

```bash
/usr/bin/python3 \
  <CODEX_HOME>/skills/k70e-rkp-ctf/scripts/verify_submission.py \
  <PROJECT_ROOT>/<DEVICE_WORKSPACE>/03_提取结果/K70E_CTF_SUBMISSION_google-rkp-sw_20260905_2244
```

预期摘要：

```json
{
  "status": "FAIL",
  "failed_checks": 1,
  "private_material_printed": false,
  "network_or_device_access": false
}
```

失败项必须是 `certificate-provisioning-info-no-not-approved`，详情命中证书 0、路径 `5/1`。如果旧包返回 PASS，说明使用的是漏检的旧 Skill，应立即停止。

验证器检查：

- 无 symlink；
- 所有必需文件存在；
- 所有目录 0700、文件 0600；
- `SHA256SUMS.txt` 不含自身、无路径穿越、完整覆盖并逐项匹配；
- 文件集合均与 Skill 内置的冻结哈希集合一致，不能通过重建清单掩盖篡改；
- identity 恰好 32 bytes，位于 P-256 合法范围；
- 纯 Python P-256 标量乘法得到的身份 SPKI 与同轮 native leaf 一致；
- 软件 PKCS#8 私钥公钥与保存公钥、Google 叶证书公钥一致；
- 四张 DER 拼接、单证书哈希和 ordered chain 哈希一致；
- 独立解析每张证书的 Provisioning Info 原始 CBOR，不丢未知键；旧包必须命中 `NOT_APPROVED`；
- OpenSSL 在签发时刻验证整条链成功；
- 每张 PEM 重新编码后与对应 DER 完全一致，组合 PEM 和中间证书 PEM 也与单证书拼接一致；
- request、fetch/sign raw body 与 HTTP metadata 哈希/长度一致；
- source zero-key、5 段 proper DICE、outer、same-run DeviceInfo 和最终软件运行报告全部满足门禁；
- 使用冻结 `rkp_sw_used.py`、固定 allowlist 的项目虚拟环境和固定 `/usr/bin/openssl` 重新解析原始 identity AuthenticatedRequest、software request 与 sign response；不从候选包、其父目录或调用者 PATH 发现会接触秘密的可执行程序，并给子进程最小环境；
- 独立复跑固定 UDS、恰好五段、逐段签名、claim profile、outer、canonical CBOR、zero-key、leaf、固定配置字段、KeysToSign/私钥、响应 wrapper、DER 排序和证书签名审计，并直接比较签名内 native challenge/DeviceInfo 与保存证据；DeviceInfo 比较区分 bool/int/float 等类型；
- 禁止 helper 写 Python bytecode，复核不会向最终包增加 `__pycache__` 或 `.pyc`；
- 冻结的 `rkp_sw_used.py` 哈希正确。

验证器不会输出 scalar、PEM 私钥或其编码内容。

## 4. 四种工作模式

### 只读验证/报告

默认模式。运行离线验证器，先读文档 52，再把文档 45–51 和旧包当历史失败证据；不访问设备或网络。

### 文档/交接

使用文档 52、旧包和文档 45–51。必须保留以下纠正：

- `_2244` 包是 `REJECTED_NOT_APPROVED`，不是最终题解；

- `_2206` 是 native per-key 补充结果，不是最终题解；
- 最终身份是 `0xdd934:x26` 的 CDI_Leaf scalar；
- TA OEM RSA 签名没有解决，实际是 SProvider RSA 结果门旁路；
- 最终请求 DeviceInfo 来自同轮 signed native source；
- 最终 CDI 轮没有单独保存逐行 fastboot transcript，重建命令不能冒充 raw log。

### 动态复现/恢复

这是原参考设备的历史动态/恢复模式。现有包不是 PASS；当前 Fenrir/SProvider/TEE 捕获会改变 DICE 1/2/4，不能作为合格签发路径。必须先找到 stock 测量完成后的 secure-world 读取原语；任何设备写入仍须人在旁并验证恢复路径。

### 另一台 K70E

先完整阅读 `references/portable-new-target.md` 和文档 50。每台设备必须从自己的 stock 备份和 baseline zero-key native CSR 建立独立 profile；baseline 文件名为 `03_baseline_csr/authenticated_request.cbor`。原机 serial、UDS、identity scalar、私钥、run-id、latch、fingerprint 和提交包一律不能复用。

`--source-init-boot` 必须是目标自己的完整 8 MiB、已经实际开机验证 `/debug_ramdisk/magisk su -c id` 与相关服务健康、再从运行分区重新转储并双端核 hash 的 known-good Magisk `init_boot_a`。未开机验证的 patch、原机 init 或仅来自文件名的“working”判断均不够。profile v3 有意固定 `_a` 布局和 `/debug_ramdisk/magisk`；不满足时应发布新版本，不得现场绕门。

只有目标 stock TA/TEE 的规定 size/SHA 精确命中 device reference，且 candidate/sidecar/结构与 toolchain 门都通过时才进入 Exact fast path。目标 fingerprint 必须是它自己的 live `ro.build.fingerprint`，不是 Exact 判定常量。任一 stock TA/TEE 不同必须停在 `PORT_REQUIRED`，按符号、交叉引用和控制流重新移植；slot、Magisk 路径或工具链不受 v2 支持则 safe-abort，不能通过改 `ready_for_automated_build` 冒充 Exact。

标准顺序增加两道不可跳过的门：capture 后必须证明其 UDS、stock CDI leaf、完整 signed DeviceInfo 和五层 DICE 都等于认可的 stock baseline；只有 `network_issuance_allowed=true` 才能联网。Google 返回后必须独立重算 `ctf_no_not_approved=true`，否则不写 SUCCESS、不 package。

capture 会在设备 `/metadata` 中原子创建 Binder keygen 持久闩锁，绑定 profile、run、capture boot ID 和精确随机远端目录 `/data/local/tmp/k70e_cdi_leaf_once_<32hex>`。正常完成必须生成 `remote_cleanup_status.json`，证明该精确目录已不存在；恢复确认、签发预检、打包和验包都重复绑定 boot/staging/cleanup 证据。

capture 中断后的规则不是一律盲目重跑：

- live 闩锁明确为 `ABSENT`、主机没有任何 post-latch 证据且 wrapper 分类为 `PRE_KEYGEN_SAFE_ABORT`：才表示可证明 keygen 未发生。保留失败目录，正常 capture 只能换一个全新 output leaf 再跑；
- 闩锁为 `CONSUMED` 或 `UNKNOWN`，或虽然 live probe 显示 `ABSENT` 但主机已有 post-latch 证据：禁止再次 keygen，只能让同一手机恢复 ADB/root 后，对原 capture 目录执行 `--resume-cleanup`；
- `--resume-cleanup` 本身 keygen 次数为 0。它先从主机副本或精确闩锁目录保存/验证 32-byte scalar 及同轮 CSR 关系，再删除唯一被闩锁绑定的远端目录并证明 absent，最后移除经等值验证的 duplicate 并完成 capture。没有可验证主机副本时宁可暂缓远端删除；可以再次运行该恢复模式，但绝不能再次运行正常 keygen。

```bash
"$PY" "$S/capture_k70e_identity_portable.py" \
  --profile "$RUNTIME_PROFILE" \
  --output-dir "$CAPTURE_DIR" \
  --resume-cleanup
```

真实签发在所有纯主机门通过后，要求同一恢复后设备 ADB/root 在线，先创建 device Google issuance latch，再创建 capture-local host attempt 目录。`attempt`、`network started`、provision summary 和 `success` 共同绑定规范化 output path 及其父目录 filesystem device/inode，防止消费闩锁后换输出路径；network/SUCCESS 还绑定私有快照中实际运行的 package auditor 和 profile helper hash。SUCCESS 先在权威 attempt 目录以 exclusive/atomic 方式提交、读回验证，再逐字节安装到 provision 目录，并递归 fsync 文件和各级目录。

签发的唯一恢复模式是 `--resume-finalize`：只允许官方 Google 请求已经完整返回“1 个新软件私钥 + 1 条链”，已有 mode 0700 的 provision 目录、attempt 和 `NETWORK_STARTED` 证据，只是最终严格审计/SUCCESS 提交被中断的情况。它不访问设备、不联网、不接受 `--server-url`，只接受缺失或逐字节相同的 proof，必要时在确认 frozen scalar 等于 canonical scalar 后删除它，重跑严格审计并完成 SUCCESS。它绝不是网络失败或不完整响应的重试机制。

```bash
"$PY" "$S/rkp_sw_portable.py" \
  --profile "$RUNTIME_PROFILE" \
  --capture-dir "$CAPTURE_DIR" \
  --output-dir "$PROVISION_DIR" \
  --resume-finalize
```

除上述窄恢复外，跨过对应 one-shot 点后的失败都按烧毁 run 处理：保留所有闩锁、目录、report、raw response 和 marker，新建 profile/run；严禁删除证据、编辑 JSON 或换 output-dir 伪造重试。

恢复确认即使 FAIL 也会留下不可覆盖的报告，本手册要求直接烧毁 run；真实签发还必须复用此前 `--preflight-only` 生成的同一份 `portable_provision_preflight.json`，不能另造或覆盖。

portable 最终包的 `04_proof/` 必须含 `remote_cleanup_status.json`、`portable_issuance_attempt.json`、`portable_network_started.json`、`portable_issuance_success.json`，以及恢复确认、capture/preflight 和 raw request/response。外部验证不能信任包内 profile 自证，必须二选一提供：

```bash
"$PY" "$S/package_verify_k70e_portable.py" verify \
  --bundle "$BUNDLE" \
  --trusted-profile "$RUNTIME_PROFILE"
```

这里的 trusted profile 必须是打包前单独保存/带外传递的普通文件，绝不能指向 bundle 内 `TARGET_PROFILE.json`；与包内文件同 device/inode 的 hardlink 或 link count 不为 1 的文件也会被拒绝。或使用在运行/打包前已经通过独立通道记录的 `--expected-profile-sha256 <64位小写hex>`，不能从待验 bundle 现抄。验证器会先把整个 bundle 冻结为私有 stable snapshot，复核源目录/文件的 file set、device/inode、mode、size 和 hash 在快照期间未变，再只在快照上做 manifest 与语义审计。证书链除签名、时间、key-match 外，还固定 Google root：DER SHA-256 `6d9db4ce6c5c0b293166d08986e05774a8776ceb525d9e4329520de12ba4bcc0`，SPKI SHA-256 `3ee44512a1af2beb39c889490c60ea3f82e43f5d5a5532f5ab9419f676cd07ec`；轮换必须独立审计，不能只信 subject/HTTPS metadata。
