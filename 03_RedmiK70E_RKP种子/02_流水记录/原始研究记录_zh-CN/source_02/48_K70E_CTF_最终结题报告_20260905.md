## 1. 执行摘要

本项目已经完成题目要求的三项同轮、自洽交付：

1. 从 K70E 当前 Open-DICE P-256 路径捕获并验证用户 `google-rkp-sw` 的最终 `CDI_Leaf` 身份标量；
2. 使用该身份与同轮设备原生 proper DICE/DeviceInfo，运行本地 `google-rkp-sw` 并新生成一把 P-256 软件私钥；
3. 向 Google Remote Provisioning 服务提交通过本地预检的请求，`fetchEekChain` 与 `signCertificates` 均返回 HTTP 200，获得一条与该软件私钥匹配的四证书链。

最终密码学关系全部闭合：身份 scalar 的公钥等于同轮 native DICE leaf；软件新私钥的公钥等于请求 `KeysToSign` 公钥和 Google 叶证书公钥；证书 DER 全消费、逐级签名有效、根自签有效，OpenSSL 链验证通过。

动态实验结束后，设备已经恢复原厂 `tee_a` 和已知良好 Magisk `init_boot_a`，正常启动，tee-supplicant namespace 中恢复原厂 TA，`vendor.teefs_state=ready`。

## 4. 技术路线概览

```text
静态逆向 KeyMint TA 的 Open-DICE P-256 活动路径
  → 定位 0xdd934 成功态 x26 的 CDI_Leaf scalar
  → 制作仅限 GenerateRkpKey caller 的一次性导出 TA
  → 保留 TA body/header digest，自身 OEM RSA 仍无效
  → exact-frame 修改 TEE SProvider：仅旁路 RSA 失败结果门
  → one-shot init_boot 在 on-fs 早绑 TA，并在 boot-complete 自动恢复磁盘 TEE
  → 同轮生成 zero-key native AuthenticatedRequest
  → 恰好一次 Binder keygen 导出 scalar
  → scalar SPKI 与同轮 native leaf SPKI 比较
  → 用完整 native AuthenticatedRequest 注入 proper DICE/DeviceInfo
  → 本地生成一把软件 key，发送前完整验证 request
  → Google fetch/sign 均 200
  → 解析并验证四证书链
  → 打包证据并恢复设备
```

这次没有获得或伪造 TA OEM RSA 私钥。成功点是最小化修改加载器决策，同时保留 TA 内容 digest 门，从而让自洽但 OEM 签名无效的研究 TA 在受控单次启动中加载。

## 12. 重要发现

1. Fenrir 属性层的 `green/locked` 与底层 `img_auth_required=0`、实际 fastboot 写入能力可以并存，不能用单一 UI/属性判断实验能力。
2. 修改 TA 的 OEM RSA 签名并未被破解；最小 SProvider 结果门旁路足以加载 body/header digest 自洽的研究 TA。
3. 早期 TEE v4 卡 logo 的根因是全量重压导致 frame 后证书/DTB 尾部截断，不是“所有修改 TEE 都无法启动”。
4. TA 替换要发生在 tee-supplicant 启动前并验证其 mount namespace；global 文件视图不足以证明实际加载。
5. `google-rkp-sw` 的 K70E 身份是 DICE 派生完成的 CDI_Leaf scalar，而不是 native 每把 RKP key 或 opaque KeyBlob。
6. 本目标的正确请求必须保留五段 proper DICE、该设备自己的稳定 UDS 和同轮 signed DeviceInfo；退化 DICE 不能代表该设备身份。
7. 把请求发送前落盘并复读验证，是防止跨轮 key/chain 混配和错误 CBOR 上网的关键门。

## 13. 限制与保留意见

- 结果针对这一台 `<DEVICE_SERIAL>`、当前固件/slot/测量态；原镜像不能直接推广到其他 K70E。另一台的可移植流程、兼容分类和新批次验收见文档 50；在第二台实机 forward test 完成前，其状态是“跨机设计已做主机回放，未做二机实测”。
- CDI leaf 会随测量变化；新轮次应做同轮匹配，不应要求历史 `64c672…` 恒定。
- 最终提交包未包含最终 CDI 轮逐行 fastboot transcript 和完整 raw earlybind/restore log；部署顺序部分由构件、状态记录和文档 44 的动态证据重建，已明确标注。
- one-shot marker 是工程型 fail-closed 保护，不是形式化事务系统；并发执行不在支持范围。
- Google 服务端行为、响应结构、配额和信任策略未来可能改变；本报告证明的是 2026-09-05 该轮成功。
- 证书有有效期；过期后仍可作为历史签发证据，但不是当前实时有效凭证。
- live `third_party/google-rkp-sw` 工作树可能继续变化；复核应以证据包内冻结源和哈希为准。

### 16.1 portable 主机验收

最终 host-only golden runtime profile SHA-256：

```text
2e39f1fabe0c660844296cbdf8542e666ce615f5df58a452db537f49b911d759
```

同一 synthetic/replay portable bundle 用两个互相独立的授权入口完成验证：

| 验证入口 | 结果 |
|---|---|
| 包外、非硬链接 `--trusted-profile` | PASS / 469 / 0 |
| 独立记录的 `--expected-profile-sha256` | PASS / 469 / 0 |
| 参考机冻结包原验证器 | PASS / 51 / 0 |

`469` 和 `51` 都是对应冻结版本的观测计数，不是跨版本合同。新的 AI 应先从项目根执行 `shasum -a 256 -c SHA256SUMS_PORTABLE.txt`，然后只接受当前入口哈希下实时输出的 `status=PASS`、`failed_checks=0` 和完整关系验证。portable PASS 不能替代原包验证，原包 PASS 也不能替另一台手机证明成功。

portable 状态机还明确支持两个且仅两个**越过 one-shot 后**的窄恢复窗口：已消费 Binder keygen 后的 `capture --resume-cleanup`，以及官方一 key/一 chain 已完整成功后的 `RKP --resume-finalize`。它们只做证据约束的幂等收尾，不产生新 key、不重放网络，也不能修复真实业务失败。另有一个尚未越过 keygen 的安全重开分支：live latch 为 `ABSENT`、没有 host post-latch 证据且 wrapper 分类 `PRE_KEYGEN_SAFE_ABORT` 时，保留失败目录并在同一有效 profile/run 下换全新 capture 输出叶；不满足这三个条件就不能据此重跑 keygen。其余跨过一次性边界的失败保存现场并建立新 profile/run。具体命令与决策见文档 46，新增风险全集见文档 47。

### 16.2 尚未关闭的限制

截至 2026-09-06，portable 六入口已完成主机 golden replay、关系验证和负向审计，但**尚未在第二台实体 K70E 上完成端到端前向测试**。因此可以声称“跨机工具、证据合同和 fail-closed 移植入口已交付”，不能声称“任意另一台 K70E 已实测可一次成功”或“不同固件无需移植”。

portable 工具也不制造 OEM/账号授权、root、可写启动链、同固件 known-good init_boot、可靠 USB/电源或安全 BROM recovery。新机缺少这些前置能力时，应把精确 blocker、已收集证据和下一步安全动作写入交接，而不是放宽门禁。

portable release 的最终判定是：**参考机题目仍为 PASS；跨设备复现包已达到可审计、可执行、遇到差异会安全停止的交付状态；第二实体机前向验证仍为明确保留项。**
