# Redmi K70E / duchamp 证书与 RKP 只读验收门禁

记录时间：2026-08-28 CST

## 1. 当前边界

候选设备来自二手描述，尚未连接本机。当前 `adb devices -l` 只看到：

```text
<DEVICE_SERIAL>  Pixel 4 XL / coral
```

因此现在没有读取到 K70E 的序列号、固件、模块、认证证书或 RKP HAL。不得把 Pixel、
xaga 或卖家文案当作 K70E 实机结论。

小米官方规格页确认 K70E 使用天玑 8300-Ultra、首发小米澎湃 OS：

```text
https://www.mi.com/redmi-k70e/specs
```

已知代号为 `duchamp`；同硬件系列还包括 POCO X6 Pro 5G。卖家描述中的“环境全过”
只说明当前软件测试结果，不能证明证书来自本机硬件、没有吊销、没有公开泄漏，也不能
证明生产 RKP 可用。

## 2. 绝对禁止项

在整个 K70E 任务中，除非用户以后另行明确授权并已有可恢复备份，禁止：

- `fastboot flashing lock`
- `fastboot oem lock`
- MiFlash 的 `clean all and lock`
- OTA/系统更新
- 跨区 ROM、降级或覆盖式刷写
- 写入 `seccfg`、`persist`、`nvram`、`nvdata`、`proinfo`、`protect1/2`
- 清除 userdata、卸载/停用现有模块

所有 ADB/fastboot 命令必须显式固定 K70E 的实际序列号；不得使用当前 Pixel
`<DEVICE_SERIAL>`，也不得沿用 xaga 序列号 `<DEVICE_SERIAL>`。

## 3. 卖家描述的风险判断

| 描述 | 对本任务的含义 |
|---|---|
| 已 root、安装很多模块 | 当前认证链可能由 TrickyStore/Keybox/Play Integrity 模块注入 |
| “证书通过” | 不能区分硬件工厂链、RKP 链或第三方 keybox |
| 基带丢失、卡一不可用 | 可能涉及 modem/NVRAM；不直接否定 Wi-Fi RKP，但会导致 SIM 国家属性为空并增加恢复风险 |
| 不能更新，更新可能锁 BL | 维持只读，绝不更新或锁 BL |
| 半永久 BL | 解锁状态可能依赖漏洞/启动链修改，不能进行任何启动链写入实验 |

这台机器可以作为只读 RKP 候选，但在完成下面第 4 节之前，不把它称为“已确认支持
RKP 的可用设备”。

## 4. 连接后的固定验收顺序

### 4.1 身份与启动状态

只读保存：

- ADB 序列号、USB transport
- `ro.product.device/product/model/brand`
- 完整 fingerprint、Android/HyperOS 版本、安全补丁
- slot、SELinux、`ro.boot.verifiedbootstate`、`ro.boot.flash.locked`
- `ro.boot.hwc`、区域、build tags
- baseband/radio/NVRAM 只读状态

### 4.2 模块和证书来源

先只列出 `/data/adb/modules`、Zygisk/Magisk/KernelSU/APatch 状态，重点检查：

- TrickyStore
- PlayIntegrityFix/PIF
- Shamiko/Zygisk Next
- keybox 注入或 attestation hook
- 自定义 `keybox.xml`、PIF JSON 与目标包配置

只导出证书，不导出或传播第三方 keybox 私钥。对每张证书记录：

- Subject/Issuer/Serial
- SPKI SHA-256 和整证书 SHA-256
- `notBefore/notAfter`
- Key Attestation/RKP OID
- 链签名和根

然后：

1. 与设备上注入 keybox 的证书链逐字节对照；
2. 查询 Google 官方 Attestation Status List：
   `https://android.googleapis.com/attestation/status`；
3. 用证书 serial/SPKI/指纹检查本工作区和公开泄漏样本；
4. 区分 `revoked`、`suspended`、公开复用、私有复用和未命中。

### 4.3 RKP HAL 协议

检查：

```text
android.hardware.security.keymint.IRemotelyProvisionedComponent/default
remote_provisioning
com.android.rkpdapp
```

通过 Binder `getHardwareInfo()` 保存：

- `versionNumber`
- `rpcAuthorName`
- `supportedEekCurve`
- `uniqueId`
- `supportedNumKeysInCsr`

AOSP 协议映射：

| `versionNumber` | Android 代际 | CSR 路径 |
|---|---|---|
| `1` | S/12 | legacy `generateCertificateRequest`，EEK + ProtectedData |
| `2` | T/13 | legacy `generateCertificateRequest`，EEK + ProtectedData |
| `3+` | U/14 起 | `generateCertificateRequestV2`，CSRv3/DICE，不再使用 EEK |

K70E 为 Android 14 首发，静态预期是 `v3/CSRv3`，但最终只接受实机 Binder 返回值。

### 4.4 原生签发验收

在证书来源和 HAL 版本确认后，再做一次原生 RKPD 验收：

1. 不卸载模块，先记录现状；
2. 使用平台 `remote_provisioning` 服务，不由主机合成 CSR；
3. 若 Xiaomi 地区等待再次只有 400 ms，只延长 Binder 回调等待，不改国家、TA 或 CSR；
4. 保存配置请求、HAL 调用、签发端 HTTP 状态和原始证书响应；
5. 若签发成功，确认叶证书对应本次设备生成的 P-256 key；
6. 若返回 444，严格记录为该设备身份未被签发端识别为已登记。

## 5. 开始实机验收所需条件

K70E 开机进入当前系统后：

1. 打开 USB 调试；
2. 在手机上确认本机电脑的 ADB 授权；
3. 保持 Wi-Fi 可用；
4. 不进入 fastboot，不点击系统更新；
5. 记录新的 K70E ADB 序列号后再继续。
