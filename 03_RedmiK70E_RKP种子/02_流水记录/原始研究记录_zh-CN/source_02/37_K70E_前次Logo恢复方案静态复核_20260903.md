# K70E 前次 Logo 恢复方案：静态复核与证据更正

日期：2026-09-03（Asia/Taipei）  
设备：Redmi K70E / `duchamp` / MT6897  
范围：只读核对镜像、嵌入代码、会话记录和主机产物。本次没有连接设备、没有刷写、没有重启，也没有执行 TA/私钥提取。

## 结论

上一份报告的总体方向是对的：应先恢复已知原版 `tee_a`，并避免把 v1 或 `clean_v3` 当作恢复基线。不过其中“v1 只是可能导致校验失败”和“循环可单独归因于 v1”的说法不够精确。现在可以把证据分成三层：

1. **静态确定的 v1 缺陷**：原版 TEE 内嵌的 Fuchsia `bin/bootsvc` 对 LZ4 `BD` 字段硬编码要求 64 KiB；实际写入的 v1 帧为 `BD=0x70`（4 MiB），会走 `bad lz4 flag (max block size must be 64k)` 错误分支。
2. **静态确定的容器不一致**：v1 还保留了旧的 BFSB `section_size`，而实际 LZ4 frame 更短；v1 同时基于含两个历史未知修改的 dump 构建。
3. **动态归因的限制**：最后一次重启前，v1 `tee_a` 与 `init_boot_clean_v3.img` 都已写入。会话只能证明“这两个状态共同存在时随后进入 Logo 循环”，不能把该次循环单独归因给某一个文件。`clean_v3` 的失败回归也不能称为对 preflash 原版 TEE 的隔离实验。

因此，v1 不应再使用；但“原版 `tee_a` + 哪个 `init_boot`”仍需作为一个独立基线组合验证，不能直接跳到 v4。

## 1. v1 的 LZ4 拒绝是可由代码闭合的

### 1.1 输入帧的实际差异

| 镜像 | SHA-256 | `FLG/BD` | block 数 | frame 长度（从 LZ4 magic 起） | BFSB `section_size` |
|---|---|---:|---:|---:|---:|
| preflash 原版 `tee_a.bin` | `18227785891a3db4119fb3055ae09bb538a6a8e9ce874876b34d287386eaf21d` | `0x68/0x40` | 69 | `0x21a5e4` | `0x21a5e4` |
| 实际写入 v1 `tee_a_patched.img` | `cb4512f7533b04ae4d2e72eb9c0fa6f6b49bd84a2f522167cee6a9474bf46e31` | `0x68/0x70` | 2 | `0x1f83c1` | `0x21a5e4`（陈旧） |
| v4 候选（静态） | `74dccbe76cd3d304af628a64dabb7121b2f3b3925021bf08f74ccfb85795d6e2` | `0x68/0x40` | 69 | `0x21a3eb` | `0x21a3eb` |

三者解压后的逻辑长度都为 4,505,600 字节；这不能掩盖 frame 描述符和边界已改变。

### 1.2 嵌入 `bootsvc` 的硬编码检查

从原版 TEE 的 LZ4 解压结果 `out/k70e_vendor/tee_lz4_decompressed.bin` 解析出 BootFS 条目 `bin/bootsvc`（BootFS 偏移 `0x1000`）。其 AArch64 函数（该 ELF 内 VA/文件偏移 `0xc038`，对应解压结果偏移 `0xd038`）执行：

```text
0xc208  ldrb  w9, [x24, 5]      ; LZ4 BD
0xc20c  and   w10, w9, 0x70
0xc210  cmp   w10, 0x40
0xc214  b.ne  0xc230
```

`0xc230` 指向错误字符串（ELF 内偏移 `0x30ec`，解压结果偏移 `0x40ec`）：

```text
bad lz4 flag (max block size must be 64k)
```

同一函数还检查独立 block、禁用 block checksum、包含 content size、LZ4 magic、content size 与输出大小一致等条件。原版和 v4 的 `BD=0x40` 满足这条上限检查；v1 的 `BD=0x70` 在解压前即走拒绝分支。这是静态代码—输入字节的确定性结论，不依赖猜测或任意 32 字节扫描。

### 1.3 BFSB 长度与来源污染

v1 的 BFSB `section_size` 仍为 `0x21a5e4`，但新 frame 实际在 `0x1f83c1` 结束；这会把外层声明长度与帧边界分离。除此之外，v1 的基底是 `tee_a_dump.img`，而不是 preflash 原版；该 dump 的解压内容在 `0x096c18–0x096c1f` 和 `0x0a6750–0x0a675f` 已有两处历史未知修改（共 24 字节）。所以即使只讨论容器，v1 也不能作为“原版只改目标点”的样本。

## 2. 会话记录能证明什么、不能证明什么

最后有完整输出的写入顺序为：

| 时间（会话 UTC） | 写入 | 记录结论 |
|---|---|---|
| 2026-09-02 09:06:38 | v1 `tee_a_patched.img` | fastboot `Sending/Writing OKAY` |
| 2026-09-02 09:07:09 | `init_boot_clean_v3.img` | fastboot `Sending/Writing OKAY` |
| 2026-09-02 09:07:14 | reboot | 命令本身返回 `OKAY` |

此前的 `BOOT_COMPLETE`（08:23、08:35）发生在另一个 TEE dump（SHA `5b99b9e63eef9d5fe76b5d236cdf1794343cbd56a77832172b6363fe5bd6f74b`）上；该 dump 已含历史补丁，不能用来证明 preflash 原版 TEE 与 Magisk `init_boot` 的组合可启动。08:26 的 `clean_v3` 回归同样只能作为“该时序/组合存在独立风险”的证据，不能改写成原版 TEE 的隔离实验。

所以当前最严谨的故障描述是：

> v1 在静态上不符合嵌入 `bootsvc` 的 64 KiB LZ4 block 限制；v1 与 `clean_v3` 同时写入后重启进入 Logo 循环。循环的单文件动态因果尚未隔离。

## 3. 恢复材料和风险门槛

可核验的 preflash 原版只有：

```text
设备备份_只读_20260831_preflash/tee_a.bin
size = 5,242,880
sha256 = 18227785891a3db4119fb3055ae09bb538a6a8e9ce874876b34d287386eaf21d
```

Windows 副本 `D:\duchamp_recovery\duchamp_tee_a_restore\tee.img` 已记录为同一哈希。现有 XML 的 `flash_list` 只有 `tee_a`，散列表中 UFS 条目为起始 `0x48800000`、大小 `0x500000`；此前成功的 SP Flash Tool 日志也确实经过 BROM、DA、UFS 和单分区写入阶段。但这只能说明恢复入口和配置曾成功用于另一个已记录的单分区恢复，不能保证当前连接、授权或卡密仍有效。

设备重新接入前不执行任何写入。接入后应先做只读枚举和状态记录；只有在用户在场、授权确认、目标分区与文件哈希再次核对且日志能逐项证明单分区写入时，才考虑恢复。不得写 preloader、seccfg、RPMB、efuse、userdata，也不得运行全量 Fenrir 安装器或自动重启脚本。

恢复后的第一目标是**原版 `tee_a` + 无诊断 overlay 的启动镜像**完成一次基线开机并记录 `BOOT_COMPLETE`。`init_boot_clean_v3.img` 不得留在基线组合中；其 SHA 为 `4c62a46c386b76fdbf403a6aff21eb79bc024a05b14f3a7d491c00eb691babf3`。精确 stock `init_boot_a` 备份为：

```text
<DEVICE_WORKSPACE>/01_设备输入/duchamp_当前启动链只读备份_20260828/init_boot_a.img
sha256 = 2efa579d35ab831675150f8e92e7f54f6437172773ae6a75c4c3322e860c1f02
```

Magisk `init_boot`（SHA `5ada320bab7e5892308491ee86db642a308852a05aeae2b1cc166a99792f4661`）曾在污染 TEE dump 上启动过，但与真正 preflash 原版 TEE 的组合仍是待验证，不能写成已知安全基线。

## 4. v4 的准确状态

v4 从 preflash 原版构建，保持 `FLG/BD=0x68/0x40`、69 个 block，仅改动落在 block 8 和 14，并同步了 BFSB `section_size`。主机上已通过 LZ4 往返解压和目标字节检查；这只证明容器机械一致性，不能证明：

- 外层 TEE/启动链签名会接受它；
- 安全世界会加载它；
- 诊断 TA 会执行；
- RKP 私钥材料会被导出；或
- 它与任何现有证书形成同一把 key 的交付闭环。

在原版基线启动和独立日志采集完成前，不把 v4 作为恢复步骤，也不把静态通过写成“设备已接受”。

## 5. RKP 交付状态（静态复核）

现有 K70E 原生结果目录仍只有一条真实 Google `signCertificates` HTTP 200 证书链：

```text
<DEVICE_WORKSPACE>/03_提取结果/K70E_google_rkp_raw_native_submit_20260829_081925/
```

叶证书有效期为 `2026-08-27 08:40:55Z` 至 `2026-09-09 04:41:24Z`，时长 `12 天 20:00:29`；provisioning-information 扩展给出滚动近 30 天约 `8` 张。该链叶公钥与同次 `MacedPublicKey` 匹配，但同目录的 275 字节 `private_key_blob_opaque.bin`（SHA `ac9ea690b6383af4717fcce3a9f2eb7c0b00f8683c89c696263646aa54d2560e`）是 KeyMint opaque handle，不是主机可读私钥。

截至本复核，仍没有能与该叶公钥逐字节匹配的 K70E raw scalar、未加密 DER 或 PKCS#8 文件；软件测试 seed、外来 `keybox.xml`、FID/FF06、CSR、MAC、签名和任意 32 字节窗口都不能替代它们。因此赛事要求的“同一把 K70E key 的私钥 + 证书”尚未完成。

## 6. 复核后的单一判断

上一份报告可以保留为恢复记录，但执行时应以本文件的证据边界为准：

```text
v1 = 静态确定不符合 bootsvc 的 64 KiB BD 检查，禁用
clean_v3 = 独立高风险 overlay，禁用
原版 tee_a = 唯一有完整哈希的恢复候选
v4 = 静态候选，未做真机验证，不是恢复基线
RKP = 证书已保存；K70E 对应主机私钥仍未形成
```
