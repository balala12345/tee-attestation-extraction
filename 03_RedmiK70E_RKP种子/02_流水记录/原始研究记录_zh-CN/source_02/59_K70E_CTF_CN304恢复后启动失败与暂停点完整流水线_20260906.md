1. `NOT_APPROVED` 的简单次数/键 1 计数风控已由现有样本排除；主因家族是服务器可见的 signed DeviceInfo/DICE/启动测量环境差异。

## 5. 启动失败的直接根因：双重 AVB mismatch

### 5.1 为什么恢复前能启动、恢复 stock LK 后不能启动

签名顶层 `vbmeta_a` SHA-256 是：

```text
8 MiB raw partition  c38281042cd2581421c4589ee2ccaf349e929d1e6a1390b915133c3bb2291ce0
前 8 KiB payload     dccb671d47a1822835cea7117b2cf3c3d896322283ddd9f6e623a959e1411d54
```

前 8 KiB 与官方 CN304 包内 `images/vbmeta.img` 逐字节一致；raw 全分区哈希不同只是因为设备备份包含后续零填充。

它使用 `SHA256_RSA2048`、flags 0，并对 `init_boot` 和 `vendor_boot` 固定 CN304 stock hash descriptor。恢复前的 Fenrir/旧解锁组合允许 AVB 不匹配的 Magisk/OrangeFox 组件启动；第 7 步恢复 stock `lk_a` 后，Fastboot 实测 `unlocked:no`、`secure:yes`，stock LK 重新强制这些 descriptor。于是两个不匹配同时成为启动阻断点。

## 12. 暂停期间的绝对禁止项

在用户明确“继续”、并且设备旁有人能报告屏幕前：

- 不操作手机按键，不连接 BROM，不发 Fastboot/ADB 命令；
- 不再点击在线签名/F2，不刷新 challenge，不重用旧 SLA response；
- 不启动 SPFT/Auth，不执行任何 READ/WRITE-FLASH；
- 不调用 Binder、zero-key collector 或 Google endpoint；
- 不重放 generic/default 444 请求，不重放任何已 consumed ATTEMPT；
- 不删除/改名/覆盖一次性 marker 和原始 stderr；
- 不打印、截图、cat、hex dump、base64 或上传 CDI 标量、软件私钥、完整 MiTEE 日志、完整 BROM challenge；
- 不用旧 `NOT_APPROVED` 链提交，不编辑 Google 签名的 Provisioning Info，不把新私钥和旧证书混合；
- 不执行裸 `oem unlock`、`flashing unlock`、relock、`flash_all*`、erase、format、wipe 或 set_active；
- 不刷 `tee*`、B 槽、RPMB、efuse、proinfo、persist、nvram、nvdata、metadata、userdata；
- 不盲写 seccfg；standard seccfg 与 Xiaomi custom/RPMB lock state 必须一起判定；

- 不用 Fenrir/patched TEE/SProvider 环境做最终 Google issuance。Fenrir 至多是经审计的临时救援引导手段，最终必须完全恢复并由 fresh DICE/DeviceInfo 验收。

## 13. 恢复工作时的决策树

### 13.1 第零步：只辨认当前状态

恢复时先要求用户在手机旁，记录屏幕原文，然后做只读 USB inventory。只允许以下四种分支：

```text
屏幕明确显示 Mi-Recovery  -> 分支 A
屏幕明确显示 OrangeFox     -> 分支 B
屏幕显示 system destroyed / 能回 Fastboot -> 分支 C
黑屏且 Fastboot/ADB 均空   -> 分支 D
```

不要先按键再问“刚才是什么画面”；证据顺序应是先观察、后操作。

### 13.2 分支 A：已目视确认 stock Mi-Recovery

1. 先拍/记版本和菜单文字，确认不是 OrangeFox；不要选择 wipe。
2. 优先测试非破坏性的 `Connect with MIAssistant`，只确认 transport 和支持能力。
3. 官方 CN304 recovery ROM 的预期整包信息是：

   ```text
   duchamp-ota_full-OS3.0.304.0.WNLCNXM-user-16.0-5dc5bd9579.zip
   expected size 7,158,375,045
   expected MD5  5dc5bd957959ffa505e3002f7fe6f2ba
   ```

   Mac 目前只有 `.part` 323,584 字节，Windows 也只有不完整 partial；它们不可刷、不可解包当完整包。只有完整下载、MD5/ZIP traversal 通过后才能评估官方 sideload/assistant 路线。
4. stock Recovery 是否会接受该包、是否保留数据、是否重写 lock/boot components 都要在执行前离线审计；不要凭菜单名称推测。

### 13.3 分支 B：已目视确认 OrangeFox

1. 先只读确认 ADB 是否出现、串号是否唯一、分区设备映射是否正确；不要立即刷。
2. 保存当前 `vendor_boot_a`、`init_boot_a`、`vbmeta_a`、`misc`/boot control 的只读哈希；不得读取或打印用户数据。
3. OrangeFox 只能作为候选临时救援 RAM/写入通道，不能成为最终 accepted issuance measured route。经专用 pair 工具审计后，用官方 CN304 `vendor_boot.img=63531c...` 和 `init_boot.img=8367dd...` 同时闭合两个 AVB descriptor；退出 OrangeFox 后再建立新的 stock postboot。这样预计会失去当前 Magisk root，日志访问能力必须作为下一道独立门解决，绝不能为图省事在最终签发环境继续沿用 OrangeFox/Magisk。
4. 任一写入都必须用事件专用脚本、固定串号/分区/大小/哈希、写前备份、写后 readback 和断电安全边界；禁止在 UI 里凭文件名手点。

### 13.4 分支 C：system destroyed 或 stock Fastboot

stock Fastboot 已实证被 lock control 拒写，重复相同 `flash init_boot_a` 没有价值。优先路线：

1. **BROM fresh auth 后先读，不先写。** 使用新的 challenge-specific response，先执行经过哈希固定的 seccfg/expdb read-only XML，并把 Windows 证据镜像回 Mac。
2. 历史同机可比锚：

   ```text

     size 8,388,608
     SHA-256 25282f96182c2b7f84155db054f2c5f0d5fab8632d9c029767d9ded74bd0a55a

     size 134,217,728
     SHA-256 2a0bfab707cbc72b6688e32d7780367a6e1cc2d30c153bcd0925ef9d3aae6c1a
   ```

   历史解析对应 standard seccfg state 3 与 Xiaomi custom/mi state 3。当前值未知，不能从 OEM toggle 或旧 root 史推断。
3. readback 判定：
   - 当前 seccfg 已等于历史 state-3：**不得重写 seccfg**；问题在 custom/RPMB 或更高层，继续只读取证/官方服务路线。
   - 当前 seccfg 非 state-3，且 custom 状态能被独立证明仍为 3：才评估同机 seccfg 窄恢复。
   - custom 为非 3 或未知：不写 seccfg，不猜 RPMB，不做裸 unlock。
4. 如果只求先恢复 locked stock boot，BROM 的两个候选目标偏移已有旧 SPFT layout 证据：

   ```text
   UFS_LU2 vendor_boot_a offset 0x43800000 length 0x4000000
   UFS_LU2 init_boot_a   offset 0x47800000 length 0x00800000
   ```

   但在重新验证 scatter/LU mapping、完整官方镜像、write XML、readback XML、供电和 auth 之前禁止执行。两者必须作为一个“双 mismatch 闭合”方案审计，不能只写 init_boot 后就假设可启动。
5. 购买/充值商业 auth 卡属于新的财务授权，必须由用户另行决定；没有授权时只保留证据，不擅自消费。

### 13.5 分支 D：黑屏且所有 transport 为空

1. 先确认电量、线材和 Windows 设备管理器；不要循环插拔和反复触发签名。
2. 尝试一次可观察的 Power+VolDown 进入 Fastboot；若出现唯一串号，回分支 C。
3. 若 Fastboot 不出现，在 Windows 上按既有双音量流程进入 BROM；只确认 `VID_0E8D&PID_0003`，没有新的 auth 能力就停止，不连接 DA。
4. 任何未知枚举或多个设备都停止；目标串号只能在 Fastboot/ADB 层验证，BROM 层必须同时靠物理唯一性和 USB 路径约束。
