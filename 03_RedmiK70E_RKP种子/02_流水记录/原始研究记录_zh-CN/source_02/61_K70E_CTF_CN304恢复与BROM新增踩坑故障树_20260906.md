## 1. 最短结论

本次故障不是“再刷一次 TEE”能解决，也不是简单 Google 次数风控。已验证的根因链是：

```text
旧恢复合同误把 OrangeFox vendor_boot 当成 stock
  + 保留 Magisk init_boot
  + 后续恢复 stock LK/stock vbmeta enforcement
  = vendor_boot 与 init_boot 两个 descriptor 同时不匹配
  -> the system has been destroyed
```

stock Fastboot 当前观测为 `unlocked=no, secure=yes`，已拒绝官方 `init_boot_a` 写入；BROM 虽取得 fresh challenge，但在线 Auth 卡密耗尽，没有 auth response、没有 DA、没有分区 IO。正确续接是：先只读识别 Recovery，再获得真实可审计写通道，然后成对恢复官方 CN304 `vendor_boot_a + init_boot_a`，绝不能再单刷 TEE、单刷 init_boot、碰 B 槽或碰锁状态。

## 4. 坑一：双重 AVB，不是单 init_boot 故障

### 现象

恢复 stock LK 后，Xiaomi logo 后显示 `the system has been destroyed`。单刷官方 init_boot 的思路看似直接。

### 原始关系

stock `vbmeta_a=c3828104…1ce0` 同时含：

```text
vendor_boot descriptor image_size  52,883,456
stored digest                      213240355a320f7db7764437dda7a103525ea1362d6148dd235c1d6aa43e3018

init_boot descriptor image_size     3,137,536
stored digest                      5baa011f4b134de75b9096251240e88a38da36ec1f06c6574d5e8fb055b888b7
```

官方 CN304 两镜像分别精确满足这两个 digest；当前 OrangeFox vendor_boot 和 Magisk init_boot 均不满足。

### 为什么以前能开、现在不能

以前的可写/可 root 现场不能证明 stock LK 当前仍允许 modified image。八步恢复把 stock LK/AVB enforcement 带回来后，两个长期存在的不匹配同时成为硬错误。OEM 解锁设置页面亮、历史 Fastboot 写成功、历史 Fenrir 日志都不能替代 fresh `getvar unlocked` 和实际验证路径。

### 修复原则

- 不再只写 init_boot；
- 同一会话成对写官方 `vendor_boot_a=63531c1f…17ef`、`init_boot_a=8367ddde…3c93`；
- 两项读回一致前不重启；
- 不改 vbmeta、不禁用 verity、不写 TEE、不碰锁状态。

## 5. 坑二：OrangeFox 被误标成 stock

### 精确实锤

以下两文件长度均为 67,108,864，SHA-256 均为 `501ec32cb585c60c4db9245266c16469eb42b31f7b4fb37b8f8f6d1c7d45d9c9`：

### 影响面

判断 stock 必须至少满足：官方包来源 hash、AVB descriptor、镜像内容/ramdisk 身份三方一致。文件名含 `stock`、目录名含 `preflash`、设备曾经开机、旧 manifest 已列入，全部都不是充分证据。

## 6. 坑三：Fastboot `OKAY` 不等于 Recovery 启动，也不等于写成功

三个容易混淆的 `OKAY`：

1. `fastboot reboot recovery` 的 `OKAY`：只证明 bootloader 接受了重启命令；手机可能回 Fastboot、进 Android、显示 destroyed 或黑屏；
2. `Sending 'partition' ... OKAY`：只证明主机把 payload 传到 bootloader 的 RAM 缓冲区；
3. `Writing 'partition' ... OKAY`：才是 bootloader 报告写阶段成功，但仍需完整 `Finished`、目标唯一性和 readback hash。

本次官方 init_boot 的原始输出就是反例：

```text
Sending 'init_boot_a' ... OKAY
Writing 'init_boot_a' ... FAILED (remote: 'No support by lock control')
```

本次失败点已定位在 lock-control gate、早于分区介质 I/O，所以该尝试没有
改变 `init_boot_a`。通用工具的 `PARTIAL_OR_UNKNOWN` marker 仍保留为不可删
的失败事件账本；它不表示已有半写物理证据。

恢复识别必须依赖手机屏幕、USB 模式和必要的 Recovery ADB 属性共同判定，不能只看命令退出画面。

## 7. 坑四：challenge ≠ auth ≠ DA ≠ IO

BROM/SPFT 状态机必须逐级证明：

| 层 | 证明什么 | 不能证明什么 |
|---|---|---|
| BROM challenge | 目标进入 BROM，设备发出本连接挑战 | 没有授权 |
| auth response | 签名服务为这次 challenge 生成响应，并被设备接受 | 不代表 DA 已加载 |
| DA1/DA2 | 下载代理实际进入并完成目标配置 | 不代表分区几何或 IO 正确 |
| READ/WRITE IO | 指定 LU/offset/length 的操作完成且有原始证据 | 写后仍需 readback/hash |

每次 BROM 重连都会产生 fresh challenge，旧 response 不能跨连接复用。Auth GUI 有文本、HTTP 返回成功、SPFT 识别 COM、进度条动、进程 exit 0，都不能越级当成下一层成功。

当前准确状态是：challenge 有；auth 失败；DA 无；IO 无。

## 9. 坑六：PowerShell/native stderr 不能按红字判失败

Android platform-tools 的 `fastboot getvar` 正常值输出到 stderr。Windows PowerShell 5.1 把 native stderr 接进管道时可能显示为红色 `ErrorRecord`；`2>&1 | Tee-Object` 后 `$?` 或管道结果可能只代表最后一个 cmdlet，不代表 Fastboot。

稳妥做法：

- stdout、stderr 分文件保存；
- 紧跟 native 进程读取并固化 `$LASTEXITCODE`，不要先跑别的命令；
- 需要严格证据时用 `Start-Process -Wait -PassThru` 配合 `-RedirectStandardOutput` 和 `-RedirectStandardError`；
- 成败同时检查退出码、目标行、`FAILED`/warning、完整 send/write/finished framing；
- 不把“红字”自动当失败，也不把 shell pipeline exit 0 自动当成功。

同理，macOS Fastboot 的正常 `getvar` 也在 stderr；解析器必须固定真实客户端格式，不能随意 trim/合并后伪造完整证据。

## 10. 坑七：远程键盘大小写、冒号和输入法

Windows App/RDP 中出现过 Shift 状态、键盘布局和 `:` 输入不可靠。风险不是“命令难看”，而是可能把 `D:\...` 变成错误盘符/相对路径，或把大小写敏感的 challenge/auth 内容输错。

规则：

- 路径尽量只用短 ASCII，避免中文 IME 介入 Auth/SPFT 文件选择；
- 冒号无法可靠输入时打开 Windows 屏幕键盘，用 Shift + `;` 输入，并肉眼复核完整 `D:\...`；
- 任何 hash、challenge、response 都不手打；从受控文件加载并验 hash；
- 输入后先做只读 `Get-Item`/`Get-FileHash`，不能直接按 Download；
- 远程点击坐标只用于已截图并确认的当前窗口，窗口移动/缩放后坐标全部作废；
- 不因窗口标题或按钮颜色推断工具已进入下一状态。

## 11. 坑八：partial ROM 不是 ROM

full CN304 Recovery ROM 期望：

```text
duchamp-ota_full-OS3.0.304.0.WNLCNXM-user-16.0-5dc5bd9579.zip
size  7,158,375,045
MD5   5dc5bd957959ffa505e3002f7fe6f2ba
```

Mac 与 Windows 的现有 `.part` 只下载了约数百 KiB；网络慢或 HTTP 有响应不代表文件完整。禁止：

- 把 `.part` 改名 `.zip`；
- 仅凭 ZIP 头就侧载；
- 用 partial 内容提取 vendor_boot/init_boot；
- 把 CDN 403、range 响应或下载进程 exit 0 当完整包证明。

只有 expected size、MD5、ZIP 完整遍历和签名/设备接受链都通过，才可用于官方 Recovery 路线。当前官方 fastboot 包中已验的 pair 镜像可作 raw 恢复源，但不能把 fastboot 包等同 Recovery OTA。

## 12. 坑九：`NETWORK_STARTED` 的范围不能扩大或缩小

`NETWORK_STARTED` 是 `rkp_sw_stock_log_once.py` 对本次 Google issuance 核心调用的耐久状态，不是整台电脑所有网络活动的总开关。

不属于该 marker 的活动：

- RDP/Windows App；
- Mac 到 Windows 的本地 HTTP；
- ROM 下载；
- SPFT/Auth 在线签名；
- ADB/Fastboot USB 通讯。

这些活动各有自己的审计与风险，但不会自动消耗 Google RKP one-shot。反过来，以下情况不能因 marker 缺失就宣布“肯定没联网”：

- `ATTEMPT` 后进程崩溃；
- HTTP 发送边界未知；
- 原始响应未落盘；
- wrapper/marker 版本漂移；
- 人工绕过 wrapper 调用了 endpoint。

Google 执行边界一旦是 `NETWORK_STARTED`、显式请求已发或网络结果未知，该 attempt 均按 consumed 处理。zero-key capture 的 `network submitted=false` 也只说明该 collector 没有提交 Google，不代表主机全程物理断网。

手机离线门是另一条独立要求：Google one-shot 时只允许主机联网，手机保持飞行模式、Wi-Fi/移动路由关闭，IPv4/IPv6 查询成功且无转发 default route。

本项目全局不能再写“`NETWORK_STARTED` 全为 0”。独立
`K70E_google_rkp_sw_vanilla_true_CDI_generic_default_20260906_172657`
负实验已经产生 fetch/sign 两个 `NETWORK_STARTED`，fetch 为 HTTP 200、
sign 为 HTTP 444 `Device not registered`。准确说法只能是：**approved-stock
专用 zero-key/Google 路线尚未消耗；generic/default 负实验已经消耗并失败。**

## 14. 额外坑：官方 init_boot 开机后 root 会消失

官方 pair 是先救回可验证 stock boot，不等于立刻能采 MiTEE 日志。现有 collector 依赖 profile 固定的 Magisk `su -c` 读取 `/data/vendor/mitee/mitee.log` 和 raw 分区；官方 `init_boot` 预计没有 root。

禁止以下错误衔接：

```text
官方 pair 能开机
  -> 忽略 root/access gate
  -> 直接运行 zero-key
  -> 调用发生但日志无法完整保存
  -> 为“重试日志”再次调 Binder
```

必须先离线设计并验证不会改变批准 DICE 的日志读取方案，或建立比赛认可、与批准基线一致的 root 路线。未解决前停在 stock postboot，不消耗 zero-key。锁状态修复不属于本 pair 恢复范围。

## 15. 额外坑：锁状态有多个域，UI/一个 getvar 都不是全貌

历史同机 `seccfg state=3`、expdb 记录、OEM 解锁开关、Fenrir 日志、Fastboot `unlocked` 和 Google signed DeviceInfo 描述的是不同层。不能因为其中一个看起来“已解锁”就写另一个域；也不能用裸 `oem unlock` 测试。

本轮明确禁止写 `seccfg`、`expdb`、RPMB、efuse 或执行 lock/unlock。若未来必须研究锁域，只能先做受授权 BROM readback、严格配对同机历史证据，并单独立项；不得把它混入官方 pair 恢复或 Google attempt。

## 16. 额外坑：TEE、B 槽和秘密材料

- `tee_a=18227785891a3db4119fb3055ae09bb538a6a8e9ce874876b34d287386eaf21d` 已是 stock；再刷 TEE 不能修 vendor_boot/init_boot descriptor，反而可能改变 DICE 或增加砖风险。
- 不写 `_b`、`*_ab`。whole-super 是旧八步的一次性例外，不是今后可以继续跨槽的许可证。
- 不把 B 槽标记 bootable，不 set_active，不用 B 槽救援试启动。
- CDI scalar、软件 PKCS#8、完整 MiTEE 日志只保存在 0700/0600 私密树；报告只写路径、大小、hash、SPKI hash、证书元数据和布尔关系。

## 17. 故障症状速查

| 症状 | 最可能解释 | 立即动作 |
|---|---|---|
| Fastboot 列表为空 | 不是 Fastboot、驱动/线/端口问题或仍在 BROM | 查屏幕与 Windows 设备枚举；不发写命令 |
| `reboot recovery` OK 后又 Fastboot | Recovery 启动被 AVB 拒绝或模式未落地 | 记录屏幕/USB；转其他写通道 |
| OrangeFox 出现 | 当前 vendor_boot 仍是第三方 | 只读鉴别，专用 pair 工具前不点写入 |
| init_boot `Sending OKAY` + `Writing FAILED` | locked stock Fastboot 拒绝 | 不重试、不 `oem unlock` |
| BROM 有 80-byte BLOB | 只有 fresh challenge | 等有效 auth；不称 DA 已进 |
| `卡密已耗尽` | 授权资源为 0 | 保全、停止；新卡/服务需用户决定 |
| SPFT 显示连接但无 DA 日志 | 仍未跨过 auth/DA | 不执行写 XML |
| ROM 只有几百 KiB | partial download | 禁止使用 |
| postboot 脚本 hash 不符 | manifest 漂移 | 离线迁移并重冻，不放宽检查 |
| stock Android 能开但无 root | 基础恢复成功，采集权限未解决 | 停在 postboot，绝不调 zero-key |
| Google HTTP 200 但 PI 有 NOT_APPROVED | 本 attempt 被拒绝 | 保全负样本；不重放；无风控信号则离线继续找差异 |
