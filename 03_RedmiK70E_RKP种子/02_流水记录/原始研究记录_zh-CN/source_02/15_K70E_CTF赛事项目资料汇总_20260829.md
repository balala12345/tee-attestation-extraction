## 1. 赛事目标

本题目标是：

```text
从目标设备取得 RKP 身份材料
    -> 使用 google-rkp-sw 或等价实现生成合法请求
    -> 在 Google/主办方沙箱取得真实签发证书
    -> 保存私钥、请求、响应、证书链
    -> 解析 notBefore/notAfter 和证书中的近 30 天签发数量
```

本项目同时记录两条路线：

- **Redmi K70E / duchamp：** 原厂 Mitee CSRv3 设备侧路线已证实可用，但尚未获得可供 `google-rkp-sw --seed` 使用的主机 IDC；当前完整调用链证据支持“UDS/CDI 私密材料留在 TEE”。
- **Nothing A142 / Pacman：** 另有独立成功案例，曾取得每把 RKP key 对应的 32 字节 P-256 private scalar，并由 `google-rkp-sw` 成功取得 Google/CTF HTTP 200 证书。它不是 K70E 的直接材料。

## 4. CSRv3 活动调用链

原始 Binder 客户端：

`<PROJECT_ROOT>/<DEVICE_WORKSPACE>/02_脚本与补丁/rkp_binder_csr_v2_client.cpp`

静态链：

```text
Binder dispatcher 0xCB31C (+0x8c)
  -> GenerateCsr 0x626C8
     -> 0x925C8 -> 0x92E18 / 0x92F60 / 0x93208
        -> 0x94D08（COSE_Mac0）
     -> 0x62CC8（上下文函数表间接调用）
     -> 0x62DCC -> 0xF5DE0
        -> 0x12CD60 / 0xF2680 / 0xF18D0 / 0xF1430
     -> 0x62DDC -> 0x91A40 -> 0x958D8（DICE 条目）
     -> 0x63498 / 0x635A8（vector append/copy）
     -> Binder CSR byte[]
```

重点：

- `0x925C8` 的 0x20 字节操作是常量时间比较，不是导出；
- `0x94D08` 组装 COSE_Mac0，不是 IDC；
- `0x62DCC -> 0xF5DE0` 的 32 字节对象是 TEE 内部临时对象；
- `0x62CC8` 的表项落到厂商安全上下文，返回状态、DeviceInfo、MAC/SignedMac 或受限 ProtectedData 对象；
- `0x91A40 -> 0x958D8` 整理 DICE 公钥链和签名；
- `0x63498/0x635A8` 只把已生成结果复制到返回 vector；
- 旧 `P256KeypairFromCDI`/`0xDA520` 只在旧辅助路径出现，不能套到活动 CSRv3 入口。

## 5. 32 字节 IDC 结论

已拒绝候选包括：

- 诊断 TA `0x158968` 固定值：前 32 字节 SHA-256 `a148ec407f21f6e0cb845577a1b26ab1339fcdb14e009a9dd509ca7fa35cd2c5`；独立派生的 SPKI 不匹配原生 UDS；
- `0x158900` 起 256 字节窗口：225 个重叠窗口，`match_count=0`；
- 活跃种子诊断第三轮结果出口标记未出现，窗口匹配仍为 0；
- EEK、公钥、MAC、签名、ProtectedData、vector 临时缓冲和 275 字节 opaque blob：都没有通过 UDS SPKI 独立重建门控。

最终限定结论：

> 对已保存的 stock TA 和一次完整 `GenerateCertificateRequestV2` 调用链，未发现主机可见、能重建原生 UDS SPKI 的私密 32 字节材料；私密 UDS/CDI 材料在该调用中留在 TEE 内。该结论不等于“设备永远不存在厂商调试出口”，但现有证据不足以称为 IDC 已提取。

当前禁止：继续扫描任意 32 字节、把 opaque blob 当 seed、把 HBK/Device Key Seed 直接传给 `google-rkp-sw --seed`，或在没有独立门控的情况下联网提交。

## 7. “本月签发次数”的正确口径

设备文件中的 `google_count` 是 RKPD 发起 Google 请求的客户端计数：

- `last_stats_day=20260828`：`google_count=2`；
- 后续备份 `last_stats_day=20260829`：`google_count=11`；
- 重连复核记录曾为 `google_count=5`。

它不是 Google 后端自然月签发总数，也不是证书条数。当前没有后端配额/账单接口证据，因此不能把 2、5 或 11 写成题目要求的真实服务端月度次数。

## 8. 外来 Keybox 与 Fenrir/救砖背景

### 外来 Keybox

设备存在 `/data/adb/tricky_store/keybox.xml`，文档记录 SHA-256：
`e14aa5f6fce07048d5d38ddc186c5ad53af54e4ad64698b098e78d190ffb8789`。

XML 自报 `DeviceID=Samsung_...`；attestation key 证书为 2018-11-28，且状态快照标记为 `REVOKED / KEY_COMPROMISE`。它是外来注入痕迹，不是 K70E 原生 RKP 身份证明。

### Fenrir 与救砖

- 原始 `lk_a` 备份 SHA-256：`9c760f784a8621682f85a58617a6332ae372cd208d41a7d4ddf475531bbfcb35`；
- 误刷镜像 SHA-256：`b5dfff784b302163156191e3879079cf6fefb0812823be8d008e3b55e61020f7`；
- 变砖原因：重组 `bl2_ext` 多 80 字节后被截断写回 `lk_a`；
- 修复：使用 V6 BROM 授权链只写回原始 `lk_a`，没有格式化、清除 userdata、修改 efuse/RPMB/seccfg 或锁 BL；
- Fenrir 目前只有静态干运行，不能称为漏洞已复现；当前不应为 IDC 任务再次刷 LK。

TA bind 标记实验显示：运行时文件哈希变化不等于安全世界已经加载新实例；TEE 会缓存旧 TA。该实验不能作为“魔改 TA 已执行”的证据。
